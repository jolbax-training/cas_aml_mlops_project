## Context

The coordinator is a Claude Opus 5.5 session in Orca. Today its working material sits in a session scratchpad: shared worker rules (`common.txt`), a fix-loop brief (`fix.txt`), a reviewer brief (`review.txt`), `wait.sh`/`waitloop.sh` (block on worker messages), `ciwatch.sh` (poll a GitHub Actions run), `STATE.md` (handoff), and example review reports. Hard-coded values (repository URL, scratchpad paths, run and dispatch IDs, terminal handles) make them unusable elsewhere. The repo has six `openspec-*` project skills under `.claude/skills/` (frontmatter `name`, `description`, then a procedural body). The `openspec-*` skills are generated by the OpenSpec CLI and carry generator values (`license: MIT`, `metadata.author: openspec`, `generatedBy`, `compatibility: Requires openspec CLI`) and no `CLAUDE.md`. See proposal.md for motivation.

## Goals / Non-Goals

**Goals:**
- A future session loads one skill and coordinates the same way: same roles, lifecycle, gates, and brief wording.
- The main file stays short enough to read in one pass; situational material is reached through pointers (progressive disclosure).
- Helper scripts are generic, runnable from the repo, and checkable offline.

**Non-Goals:**
- No new process, role, or gate beyond the user-approved description.
- No change to Orca, the existing `openspec-*` skills, CI workflows, or evaluator code.
- No recorded results: the skill states procedure, not run IDs, hashes, or review verdicts.

## Decisions

1. **One skill, `orchestration-workflow`, with reference files.** `SKILL.md` holds roles, the seven-step lifecycle (propose, implement, review, fix loop, merge, CI-red repair, archive), mechanics essentials, and guardrails. Reference files sit beside it: `briefs.md` (worker, fix, review templates), `merge-and-ci.md`, `recovery.md`, `state-template.md`. Each is reached through a pointer that names its branch ("when merging…", "when a reviewer stalls…"). *Alternative:* one long file (rejected: sprawl, situational recovery text buries the steps); one skill per role (rejected: the coordinator needs the whole loop, and the roles share the guardrails).
2. **Frontmatter description is a trigger pointer.** It leads with the coordinator role and lists the distinct branches that should load the skill (dispatching or supervising Orca workers, reviewing or fixing a change, merging and watching CI, handing off a session), without restating the body. It carries no `allowed-tools` restriction, since the coordinator needs shell, git, and `orca`.
3. **Briefs are templates with named placeholders** (`<change>`, `<branch>`, `<report-path>`, `<test commands>`), not literal text with IDs. The shared worker rules keep their content (roles, no push/merge/archive, commit trailer, honest task ticking, evidence in `worker_done`) and phrase targets positively, keeping prohibitions only for hard guardrails (paid calls, invented evidence, user reflections), each paired with the positive action. Test commands and the image note are project facts the template names once.
4. **Scripts live in `scripts/orchestration/`, are POSIX `sh`, and take parameters.**
   - `wait.sh [ack_delivery]`: one blocking `orca orchestration check --wait` for `worker_done,escalation,question` messages, prints a readable summary.
   - `waitloop.sh [ack_delivery]`: repeats `wait.sh`, acking each non-terminal batch and returning when a `worker_done`, `question`, or `escalation` arrives; the actionable delivery is **printed and its id left for the caller to ack explicitly**, because an unacked batch is replayed and hides newer mail. Loop count and timeout are parameters.
   - `ciwatch.sh <run_id>`: polls the run until completed, then prints run, jobs, failing steps, and check-run annotations (annotations rather than logs, which need authentication). The repository comes from `--repo`/`CIWATCH_REPO` or the `origin` remote, not a literal. Poll interval is a parameter, default gentle enough for the unauthenticated 60 requests/hour limit.
   - Common helper: `orca`, `curl`, and `python3` are looked up on `PATH`, so tests substitute stubs. A `--dry-run`/`--help` path prints the resolved command without calling Orca or GitHub.
   *Alternative:* Python scripts (rejected: the originals are shell and mostly glue, and tests of stubs are equally easy; keeps one idiom with the existing `scripts/ci_*.sh`).
5. **Checks for the scripts are stub-based pytest tests** under `tests/`, with fake `orca` and `curl` executables on `PATH` and canned JSON. They run in the existing offline test group, need no network, Orca, or Podman, and cover: summary output, ack passing, replay-pitfall handling, loop termination, repo resolution, completed/failed run printing, and `--dry-run`.
6. **Pointers.** `README.md` gets a short section naming the skill and when to load it. `CLAUDE.md` is not created; if it exists when the task runs, a one-line pointer is added.
7. **Consistency with `openspec-*` skills.** Same frontmatter keys (`name`, `description`, `license`, `compatibility`, `metadata`) with project-authored values: `metadata.author` is this project, no `generatedBy`, `compatibility: Requires the orca CLI, git, and the uv-managed test environment`, and no `license: MIT` copied from the generated skills unless the repository states one; imperative step wording, and references to those skills by name rather than copying their steps. The apply and archive procedures stay in those skills.
8. **Generalization rules.** Replace scratchpad paths with the single placeholder `<report-path>` wherever a brief says where a report or file goes, the repository URL with `<owner>/<repo>` resolved at runtime, and run/dispatch/terminal IDs with placeholders. The word "scratchpad" may therefore appear in prose; identifiers must not. Example review reports are mined for the report format and severity scale only; no report content or run identifiers are copied. `STATE.md` becomes a template with section headings (merged/archived, in flight, remaining, CI status) and no historical entries.
9. **Handoff state file location.** The live file is `STATE.md` at the root of the primary checkout (the one on `main`, where the coordinator runs), and it is **Git-ignored** (`/STATE.md` added to `.gitignore`), not committed: it carries run, dispatch, and branch identifiers that are session facts, and committing it would put them in history and on `main`. It must hold no secrets, no email addresses, and no API keys; run IDs, dispatch IDs, branch names, commit hashes, and CI run IDs are allowed. `SKILL.md` tells a new coordinator to read it first, and to create it from `state-template.md` when absent. Because it is ignored, a fresh clone starts without it; the template and the `docs/progress.md` evidence are what survive in Git. *Alternative:* a fixed path under the user's home (rejected: not discoverable from the repo, and mixes projects); a committed file (rejected for the reason above).
10. **Recovery playbook source.** The playbook is written strictly from the coordinator's first-hand incident record, which has seven entries: Orca quit/restart mid-run (re-open Orca, rebind to the run, redispatch each affected task with `--task` and `--retry-of`; the worktree and branch survive); Fable reviewer blocked by safeguards (stop and abandon the dispatch, keep its partial report under a new name, ask the user, use Opus 5.5 for that change only after approval, never switch reviewer model without approval); reviewer or worker cut off by an API error such as sleep mid-response, which is the **stalled reviewer** entry (no heartbeats and no `worker_done`; send the same terminal a message to continue, write the report to the report path, and send `worker_done`); replayed deliveries (ack every delivery, actionable ones included, by passing the previous delivery id with `--ack`); CI logs not accessible (poll about every 150 s, read jobs, steps, and check-run annotations through the API; reproduce red CI on Linux locally; verify fixes on a `ci/**` branch; check CI for every push to main); sandbox tests flaky under host load (grep pytest output for `failed`, rerun once and inspect load; the root fix was in the tests); and architecture-specific CI failure (an arm64-pinned committed config failed only on amd64; prefer host-independent artifacts). The "stalled reviewer" entry therefore has a source and needs no invention; where the record is silent (for example how long to wait before intervening, or when to escalate to the user) the playbook says so and tells the coordinator to ask the user rather than assert a threshold. The record is supplied to the stage-2 implementer by the coordinator in the dispatch (it lives outside the repository).
11. **Orca CLI constraints recorded in the mechanics** (from `orca orchestration --help`): (a) `--types` is only the wake condition; a returned delivery is always the whole FIFO batch and a bound run replays the oldest unacked batch even with `--types`, which is why heartbeat-only batches reach the loop; (b) reusing `--terminal` requires passing `--worktree` for that terminal and cannot be combined with `--model`; (c) `--retry-of` needs `--task` naming the failed task (`--spec` creates a new one) and does not inherit placement. Flag details are checked against `--help` at implementation time.
12. **Wait scripts report errors clearly.** Like the CI watcher, `wait.sh` and `waitloop.sh` keep stderr out of the JSON stream (filtering `_keepalive` lines), and when the response is not parseable JSON or carries an error they print that response and exit non-zero instead of a misleading summary.
13. **Named commands in guardrails.** The skill names `scripts/build_work_log.py` (with `--check`) for "rebuild the work log after milestones" and notes that `--i-accept-cost` is the flag of the OpenRouter and experiment CLIs documented in the README, so a session does not rediscover either. The merge checklist includes both.
14. **Pitfalls recorded where they bite.** Actionable deliveries must be acked or are replayed (in the wait-loop step and in `recovery.md`); grep test output for `failed` rather than trusting exit codes (merge checklist); CI-red repair never uses skips or weakened guards and is verified on a `ci/**` branch first; Orca restarts kill worker terminals, so redispatch with `--retry-of`.

## Amendment (2026-11-01): gaps from the first handover test

Task 4.1 was carried out once, in a single handover: a new coordinator session took over the paid phase (OpenRouter price recheck and smoke trials) using the skill. It is one test, not a series. It exposed seven gaps, folded into this change rather than a new one because the skill is merged but not archived. The skill files were edited afterwards, in the implementation phase (task section 5).

15. **Command facts (gap 1).** `pyproject.toml` has no build system and the README states the code is not installed as a package, so module CLIs run from the repository root with `PYTHONPATH=src`; pytest alone works without it through `pythonpath = ["src"]`. The skill states this once, next to the test commands.
16. **Command source (gap 2).** The coordinator and its briefs take commands from `README.md` and `docs/demo.md`, which hold the verified commands, and do not guess module names. Observed counter-example: `python -m codegen_eval.experiment` is a library module without a `__main__` block and exits 0 silently; the CLI is `codegen_eval.experiment_cli`. The silent exit is a separate finding for `docs/progress.md`; this change does not touch product code under `src/`.
17. **Coordinator-own steps (gap 3).** The coordinator may do small mechanical steps itself: ticking tasks with evidence, archiving, resolving documentation merge conflicts, a no-code research step such as a price recheck, and a one-line script fix with a regression test. All other code and spec changes go to workers. Paid commands are run by the coordinator itself, only after user approval, because `OPENROUTER_API_KEY` (and, as the worker brief already says, any API key) must never reach a worker brief. This refines "workers implement" and the paid-call guardrail; it adds no role.
18. **Failed paid step or gate (gap 4).** The coordinator stops spending, reports the evidence and the options with a cost cap per option, and lets the user decide. Any retry needs explicit approval with a cap (for example at most 5 tries or CHF 0.02).
19. **One Orca run per coordinator session (gap 5).** The run is created explicitly with `orca orchestration run-create` at the first dispatch and reused for every later dispatch. A coordinator never waits, acks, or dispatches in another coordinator's run, because, per `orca orchestration check --help`, all listeners on one run inbox get the same delivery and `--ack` acknowledges it for the run, so the other coordinator would lose the batch.
20. **Handover procedure (gap 6).** Handing the role to a new session: update `STATE.md` from the template, launch with `orca agent launch --agent claude --surface terminal --model claude-opus-5-5 --worktree path:<primary checkout> --prompt "<load the skill, read STATE.md, continue>"`, and let the new session create its own run. The old coordinator keeps only its in-flight changes. The detail goes to a new reference file `handover.md` so `SKILL.md` stays under about 150 lines (it has 51 now); `SKILL.md` gets a short pointer and the shorter rules (15 to 19).
21. **Concurrent coordinators (gap 7).** `STATE.md` splits ownership by change (one coordinator per change, with its run id), runs are separate, and each coordinator rebases around the other's edits to shared docs (`docs/progress.md`, `README.md`, `docs/work_log.toml`), keeping its own edits small and self-contained. `state-template.md` gains an owner and run-id field per change. Run ids are session facts that stay out of the template, which holds placeholders only. The rules live in `handover.md` with a pointer in `SKILL.md`.
22. **Briefs.** `briefs.md` gets the `PYTHONPATH=src` note and the "commands come from README.md and docs/demo.md" rule in the shared worker rules, and states that the worker brief never contains an API key.

Risk: the handover launch flags are taken from the handover test and were exercised once; the implementation checks them against `orca agent launch --help` and records any difference.

## Risks / Trade-offs

- [Skill drifts from how work is actually done] → Reference files cite the one place each fact lives (scripts, briefs); Fable reviews the skill against the approved description; `STATE.md` template keeps run-specific facts out of the skill.
- [Orca CLI flags change] → The skill names flags as used today and points to `orca orchestration --help` as the authority; scripts isolate Orca calls in one wrapper.
- [Stub tests pass while real Orca/GitHub behave differently] → Tests are labelled as stub checks; real behavior is exercised only when a session uses the scripts, and a task records that this was not verified against live services unless it is.
- [Wording too long for agents] → Main file kept to the lifecycle and guardrails; everything situational is disclosed behind pointers.
- [Unauthenticated GitHub API rate limit (60/h)] → Default 150 s poll, annotation lookups only on completion.

## Migration Plan

Additive, plus one `.gitignore` line. Merge like any change (fast-forward by the coordinator, then watch CI). Rollback is deleting the skill directory, `scripts/orchestration/`, the tests, and the README section. The scratchpad originals remain untouched.
