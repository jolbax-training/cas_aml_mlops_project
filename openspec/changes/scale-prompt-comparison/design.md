# Design

## Context

Findings from reading the code (not assumptions):

- `experiment.py` fixes `EXPERIMENT_ID = "prompt_comparison_v1"` and `TRIALS_PER_TASK = 3`; `build_config` takes neither as a parameter, and `config_drift` rebuilds with the module constants. The variant set is fixed to `("baseline", "revised")`, in that order, by `parse_config`. `schedule`, `trials_per_task` and `parse_config`'s schedule-length check are already generic, as are `run_recorded` (`trials_per_task` from the configuration) and `verify_schedule`.
- The same variant can be run twice under one experiment: `check_preconditions` rejects a second run of a variant (`prior_run`, read from `<bundle_root>/<run_id>.experiment.json` markers of the same experiment id) unless `--allow-rerun` is given, which is recorded in the marker. Run IDs are chosen by `new_run_id()` (UTC timestamp plus six hex characters); the CLI has no `--run-id`, and the run prints `bundle: <path>`. A bundle is `<bundle root>/<run_id>/`.
- The bundle root is already configurable: `--bundles` on `check`, `run` and `compare`, before the subcommand on `trace_inspect`, and after `record`/`status` on `mlflow_tracking`. Default `run_bundles` is unchanged. No code change is needed for separate bundle storage.
- `check` gates (all recomputed on each start): `cost_acceptance`, `api_key`, `variant_prompt`, `config_current` (configuration against the repository), `container_host`, `benchmark_freeze`, `probes` (probe record bound to the evaluator code hash, which hashes every `*.py` under `src/codegen_eval/`, so any code change in this change invalidates earlier probe records), `settings_frozen` (freeze record must name this experiment id and settings hash), `smoke_trace` and `calibration` (recomputed from the retained smoke bundle named in the freeze record), `budget_projection`, `prior_run`.
- Evidence is read from `--evidence` (default `DEFAULT_EVIDENCE_DIR`, `experiments/evidence/` under the package root, so this worktree's directory, which does not exist here; v1's real evidence is in the primary checkout), where `record-probes` and `freeze-settings` write `probes.json`, `probes.junit.xml` and `settings_freeze.json` with fixed names and replace them without question. Run from the primary checkout without `--evidence`, they would overwrite v1's record. `write_config` likewise rewrites the file at `--config` (default `experiments/prompt_comparison_v1.json`) unconditionally, and `build-config --trials-per-task 10` with no `--config` would turn v1's file into a 100-entry schedule.
- `compare` and `compare_runs` take the variant names from their position (`--baseline`, `--revised`) and verify each bundle against that variant's prompt, so they cannot compare a baseline with a baseline repeat. `_identity_differences` already encodes "only the prompt may differ" and requires equal `schedule_sha256`, `settings_hash` and `evaluator_code_sha256`.
- `record_bundle` (MLflow) takes `experiment=` (default `codegen-eval-runs`, used by v1); `experiment_cli run` offered (before this change) only `--tracking-uri`/`--no-tracking`; `run --experiment` is added here, and the sequence still uses `--no-tracking` and `mlflow_tracking record --experiment <name>` afterwards, as v1 did.
- The budget projection in `check` is the ledger total plus the worst case of every variant still to run: attempts = trials x (4 model calls + 2 retries per trial) at the pre-send reservation per attempt. It prints nothing unless it fails.

See proposal.md for motivation.

## Goals / Non-Goals

**Goals:**
- Run the A-B-A experiment through the existing preconditions, with the same frozen settings and bundle/evidence formats.
- Make it impossible for the v2 tooling to overwrite any existing configuration or evidence file by a missed flag, and prove the defaults unchanged by tests.
- A deterministic offline analysis with Wilson intervals and a run-to-run comparison.

**Non-Goals:**
- No new paid smoke, no new freeze of different settings, no change to prompts, benchmark, limits, model configuration or the grading code path.
- No change to the presentation, report or their evidence scripts; no change to v1 documents beyond an optional dated pointer note (see Decision 7).
- No significance tests, no claim of improvement, no interleaving implementation (Decision 6).

## Decisions

**1. A separate experiment id, configuration and trial count.** `build_config` and `config_drift` gain `experiment_id` and `trials_per_task` parameters whose defaults are the v1 constants; `build-config` gets `--experiment-id` and `--trials-per-task` (defaults v1) and drift checks rebuild with the recorded values. The configuration `experiments/prompt_comparison_v2.json` is generated by `build-config --experiment-id prompt_comparison_v2 --trials-per-task 10 --revised-prompt baseline_agent_v2 --container-platform arm64 --config experiments/prompt_comparison_v2.json` (the platform is pinned to v1's recorded one so the command is the same on every host). Its `settings`, `benchmark` and `variants` sections must equal v1's (a test and a recorded command compare them); only `experiment_id`, `trials_per_task` and `schedule` (100 entries, `task_major`, trial ids `strings_01-t1` ... `-t10`) differ. Alternative considered: reuse the v1 experiment id with 10 trials: rejected, the `prior_run` guard and run markers would collide with v1's, and the v1 configuration would have to change.

**2. Three runs under one experiment: baseline, revised, baseline `--allow-rerun`.** The existing `prior_run` precondition already treats a repeat as a recorded decision; the third run's marker records `allow_rerun: true`. The v2 bundle directory holds exactly three runs (`<id>` + `<id>.experiment.json` each), so the first two have no prior run of their variant. Alternative: a third variant name `baseline_repeat`: rejected, it widens `parse_config`, `verify_schedule` and `compare_runs` for a variant that is the baseline, and the identical variant name is what makes the three bundles pass the same schedule, prompt and identity checks.

**3. Storage: v2 writes only to its own paths.** User decisions recorded here.
- Bundles: `$P/run_bundles_v2/` where `$P` is the primary checkout (`/Users/jolbax/Developer/devspace/cas_aml_mlops_project`), next to but never inside `run_bundles/`, passed as `--bundles`. The path is already excluded through the primary checkout's `.git/info/exclude`, which every worktree shares; neither main's nor this branch's `.gitignore` is edited.
- Evidence: `experiments/evidence_v2/` in the worktree (`EV`), tracked and committed on this branch: `probes.json`, `probes.junit.xml`, `settings_freeze.json` (plus analysis outputs worth keeping, in `experiments/evidence_v2/analysis/`). v1's evidence is Git-ignored because the freeze record stores an absolute smoke-bundle path and machine facts; committing v2's is the user's accepted exception, and `check` / `run` keep passing `--smoke-bundle $SMOKE`, so the absolute path in the record is not relied on.
- MLflow: same service, experiment `codegen-eval-prompt-comparison-v2` (`mlflow_tracking record --experiment ...`), so the v1 runs in `codegen-eval-runs` are not touched. `run` also gets `--experiment` (default unchanged) so a forgotten `--no-tracking` cannot record v2 into the v1 experiment.
- Retained smoke evidence is reused read-only: `freeze-settings --smoke-bundle $SMOKE` (the v1 smoke bundle `$P/run_bundles/20261103T050806Z-30949f`; `calibrate` only reads it and checks model-config hash and image). The settings and model are identical, so no new paid smoke is needed.

**4. Overwrite guards (the only changes to existing commands).** `write_config`, `write_settings_freeze` and `write_probes_evidence` refuse to replace an existing file (and the junit file beside the probe record) whose content differs from what would be written; for the configuration, writing identical bytes is a no-op (`build-config` then says `unchanged`); a settings freeze or probe record is refused whenever any file exists, whatever its content (a probe record always differs by its timestamp). `record-probes` checks before running the suite, so a refusal costs nothing. The message names the path and says to remove it deliberately to replace it. This covers every missed-flag case: a `--config` or `--evidence` left at its default, with or without `--experiment-id` or `--trials-per-task`, cannot change v1's configuration or any evidence file. Consequence: regenerating a configuration (for example setting the revised prompt later, as v1 did) or re-recording probes after a code change needs the old file removed on purpose; for v2 that is the coordinator's own file under `experiments/evidence_v2/`. Alternatives: a guard keyed on experiment id only, which a missed `--experiment-id` defeats; deriving the evidence directory from the experiment id, a larger change. Tests prove: defaults unchanged (`build_config()` without the new arguments, built for v1's recorded platform, equals the recorded v1 sections (the default platform is the host's, and CI is amd64); `build-config --check` passes on v1; default `--bundles` is `run_bundles`), each refusal leaves its target byte-identical, and the v1 configuration's sha256 is the same before and after the whole change.

**5. Analysis: `codegen_eval.scale_analysis`, offline, no model client, no ledger, no sandbox.** `python -m codegen_eval.scale_analysis --config C --bundles B --baseline RUN_A --revised RUN_B --repeat RUN_C [--json]`. For each run it calls the existing `summarize_bundle`, `verify_schedule(bundle, config, variant)` (A and C as baseline, B as revised) and `variant_metrics`, so the figures are the same as `compare`'s; adds per-task `k/10` and the Wilson 95% interval for `primary.count / primary.of`:

    centre = (p + z^2/(2n)) / (1 + z^2/n);  half = z * sqrt(p(1-p)/n + z^2/(4n^2)) / (1 + z^2/n);  z = 1.959964

reported to four decimals, `[max(0, centre - half), min(1, centre + half)]`. Each run also reports its charged CHF (`cost.charged_chf`), and the command prints the total over the given runs against the CHF 1 stop limit (exit status 3 when exceeded; the three run IDs are optional so it can be called after each run). It then reports two pairs with identical rules to `compare_runs` (identity check through `_identity_differences`, both runs headline-eligible, otherwise "not comparable" with reasons): baseline vs revised (the effect of the prompt plus any drift) and baseline vs repeat (variation of the same prompt, plus drift over the same span). Each pair lists the difference in successes, gained/regressed/unchanged tasks and whether the two Wilson intervals overlap, nothing else: no p-values and no "significant". Interval overlap is a descriptive aid, not a test; the baseline-vs-repeat difference is reported as the observed run-to-run variation and is the yardstick for the revision's difference. Output is plain text or sorted-key JSON, identical on every call for the same bundles (no timestamps of its own). `compare_runs`, `variant_metrics` and `render_comparison` are not changed; the module imports the first two of those and the private `_identity_differences` within the same package. `experiment_cli compare` stays usable for baseline vs revised of v2 (`--config` and `--bundles` pointing at v2). Wilson with n = 100 trials ignores that the ten trials of one task are correlated and the tasks are not a random sample; the write-up says so. Tested with fixture bundles built like those in `tests/test_experiment.py` plus unit tests of the interval (0/100, 100/100, 50/100, 29/30 against the formula).

**6. Interleaving at trial level: not built.** `run_variant` writes one bundle per variant with the variant and prompt in the bundle identity, and `verify_schedule`, `compare_runs` and MLflow recording all assume one prompt per bundle. Alternating the prompts inside one schedule would need a different runner, two bundles written concurrently (or a mixed-prompt bundle format) and changes to every verifier: not small. Trade-offs if built later: it would cancel provider drift exactly per task (the best control), but sequential A-B-A with a repeat already brackets drift and measures run-to-run variation, which interleaving alone does not. A-B-A stays the default.

**7. v1 documents.** v1 files are not edited. If the user wants a pointer from `docs/prompt_comparison.md` to the v2 comparison, only one dated note line is added at the end of the document in the follow-up that writes the v2 results; this change adds none now and says so in its report.

**8. Command sequence for the coordinator.** All commands run from the worktree root of the branch carrying the implementation, at its final commit; `src/codegen_eval/*.py` must not change between `record-probes` and the last run, because the evaluator code hash is compared across the three runs and with the probe record (record that commit with the results). Commands are written out literally, with no command variable; the plain path variables below work in zsh and bash, and every use is double-quoted. `PYTHONPATH=src` is exported once (the package is not installed in the venv).

    export PYTHONPATH=src
    P=/Users/jolbax/Developer/devspace/cas_aml_mlops_project
    CFG=experiments/prompt_comparison_v2.json
    B="$P/run_bundles_v2"
    EV=experiments/evidence_v2
    SMOKE="$P/run_bundles/20261103T050806Z-30949f"
    PR="$HOME/.codegen_eval/pricing_2026-11-03.json"

Once (no key; Podman only for the probes). `build-config --check` must say "configuration matches the repository"; `record-probes` runs the Podman probe suite (skipped must be 0) and is refused, before the suite runs, if a probe record already exists; the settings freeze is committed with this change, so `freeze-settings` is only needed if `experiments/evidence_v2/settings_freeze.json` is absent. Commit `probes.json` and `probes.junit.xml` afterwards.

    .venv/bin/python -m codegen_eval.experiment_cli build-config --check --config "$CFG"
    .venv/bin/python -m codegen_eval.experiment_cli record-probes --config "$CFG" --evidence "$EV"

Per run, in this order, waiting for each command to finish. The `check` must print `all preconditions hold` (the key is read from the environment by the CLI, as in v1). The `run` prints the `bundle:` and the run ID to note. The `verify` must say COMPLETE, 100 of 100. The `scale_analysis` prints the charged CHF per run and the total.

Run 1, baseline:

    .venv/bin/python -m codegen_eval.experiment_cli check --variant baseline --config "$CFG" --evidence "$EV" --bundles "$B" --pricing "$PR" --smoke-bundle "$SMOKE" --i-accept-cost
    .venv/bin/python -m codegen_eval.experiment_cli run --variant baseline --config "$CFG" --evidence "$EV" --bundles "$B" --pricing "$PR" --smoke-bundle "$SMOKE" --i-accept-cost --no-tracking
    .venv/bin/python -m codegen_eval.trace_inspect --bundles "$B" verify RUN_1
    .venv/bin/python -m codegen_eval.scale_analysis --config "$CFG" --bundles "$B" --baseline RUN_1

Run 2, revised:

    .venv/bin/python -m codegen_eval.experiment_cli check --variant revised --config "$CFG" --evidence "$EV" --bundles "$B" --pricing "$PR" --smoke-bundle "$SMOKE" --i-accept-cost
    .venv/bin/python -m codegen_eval.experiment_cli run --variant revised --config "$CFG" --evidence "$EV" --bundles "$B" --pricing "$PR" --smoke-bundle "$SMOKE" --i-accept-cost --no-tracking
    .venv/bin/python -m codegen_eval.trace_inspect --bundles "$B" verify RUN_2
    .venv/bin/python -m codegen_eval.scale_analysis --config "$CFG" --bundles "$B" --baseline RUN_1 --revised RUN_2

Run 3, baseline repeat. The first command (the `check` without `--allow-rerun`) must print exactly one unmet precondition, `prior_run`, naming run 1, which confirms that run 1's marker is seen; the second and third carry `--allow-rerun`:

    .venv/bin/python -m codegen_eval.experiment_cli check --variant baseline --config "$CFG" --evidence "$EV" --bundles "$B" --pricing "$PR" --smoke-bundle "$SMOKE" --i-accept-cost
    .venv/bin/python -m codegen_eval.experiment_cli check --variant baseline --allow-rerun --config "$CFG" --evidence "$EV" --bundles "$B" --pricing "$PR" --smoke-bundle "$SMOKE" --i-accept-cost
    .venv/bin/python -m codegen_eval.experiment_cli run --variant baseline --allow-rerun --config "$CFG" --evidence "$EV" --bundles "$B" --pricing "$PR" --smoke-bundle "$SMOKE" --i-accept-cost --no-tracking
    .venv/bin/python -m codegen_eval.trace_inspect --bundles "$B" verify RUN_3
    .venv/bin/python -m codegen_eval.scale_analysis --config "$CFG" --bundles "$B" --baseline RUN_1 --revised RUN_2 --repeat RUN_3

After each run, stop and ask the user if the run printed `complete=False` or exited non-zero, if the printed `CHF 10 checkpoint reached` is `True`, or if the charged total exceeds CHF 1 (`scale_analysis` exits 3). No stop exists inside a run below the CHF 15 ceiling; the rule is applied between runs only.

After the three runs (MLflow service up, free): the `record` command once for each of RUN_1, RUN_2 and RUN_3 (replace RUN_N), then the comparison and the analysis in text and JSON, saved under `experiments/evidence_v2/analysis/`:

    .venv/bin/python -m codegen_eval.mlflow_tracking record RUN_N --bundles "$B" --tracking-uri http://127.0.0.1:5001 --experiment codegen-eval-prompt-comparison-v2
    .venv/bin/python -m codegen_eval.experiment_cli compare --config "$CFG" --bundles "$B" --baseline RUN_1 --revised RUN_2
    .venv/bin/python -m codegen_eval.scale_analysis --config "$CFG" --bundles "$B" --baseline RUN_1 --revised RUN_2 --repeat RUN_3
    .venv/bin/python -m codegen_eval.scale_analysis --config "$CFG" --bundles "$B" --baseline RUN_1 --revised RUN_2 --repeat RUN_3 --json

**9. Projected cost** (offline, `PriceInputs.reservation_chf` with `~/.codegen_eval/pricing_2026-11-03.json` and the model configuration `openrouter_glm_v1`: 12,000 input and 2,000 output tokens per attempt, margin 0.25): CHF 0.0008197 per attempt. A run is at most 100 x (4 + 2) = 600 physical attempts. What `check` compares with the CHF 15 ceiling is the ledger total (read by the CLI, not by this change; about CHF 0.0068 after v1 according to the v1 write-up) plus, for run 1, the worst case of both variants not yet done (1,200 attempts, CHF 0.9836), for run 2 the revised variant (600 attempts, CHF 0.4918), for run 3 the repeat (600 attempts, CHF 0.4918). Worst case for all three runs: 1,800 attempts, CHF 1.4755 (v1's equivalent was 360 attempts, CHF 0.2951 plus the ledger total, the CHF 0.2962 recorded). Expected spend is far lower: v1 charged CHF 0.00275 and 0.00297 for 30 trials, so about CHF 0.009 to 0.010 per 100-trial run, about CHF 0.03 for all three. Decision of the user: the CHF 1 stop rule is on actual charged spend of the v2 runs (sum of `cost.charged_chf` over the v2 bundles, checked between runs), and the worst-case reservation (CHF 1.4755 for three runs) is accepted: it is under the CHF 10 checkpoint and the CHF 15 ceiling.

### Backup slide (Decisions 9 to 14)

**Decision 9: scope, location and commit.** One self-contained HTML page for questions after the talk, shown on a projector (landscape 16:9, no scrolling at 1920x1080, one landscape A4 page when printed). Generator `scripts/build_backup_slide.py`; user text and output in a new top-level folder `backup_slide/` (`user_text.toml`, `backup_slide.html`), outside `presentation/` and `report/`. The page is committed, like the deck, so it can be opened and printed without a build; `--check` fails when the committed page differs from a fresh build, and a CI step runs it. The generator is a script, not a `src/codegen_eval` module, so no evaluator code changes and the probe record stays valid. The presentation is read-only here: only `presentation/deck/deck.css` (colours, fonts, geometry, floors) and `presentation/assets/zhaw_rgb.jpg` (sha256 `bd181c82...` as in `presentation/manifest.json`) are read; the builder verifies that hash and embeds the logo as a data URI (about 200 KB, small in a corner, with its alt text). The deck's CSS is not imported at run time: the page carries its own inline copy of the same tokens (`--ink #111111`, `--accent #0b4f8a`, `--muted #3d3d3d`, warning-slot colours, `system-ui`), with a test that the values equal those in `deck.css`.

**Decision 10: inputs are committed evidence only.** v2: `experiments/evidence_v2/analysis/scale_analysis.json`. v1: a new committed extract `experiments/evidence_v2/analysis/scale_analysis_v1.json` (and `.txt`), produced once in the implementation phase by the existing command, read-only on the primary v1 bundles: `PYTHONPATH=src .venv/bin/python -m codegen_eval.scale_analysis --config experiments/prompt_comparison_v1.json --bundles "$P/run_bundles" --baseline 20261103T053309Z-280182 --revised 20261103T095324Z-d25905 --json` (and without `--json`), `$P` being the primary checkout (all values literal in the task). Confirmed from the code: `scale_analysis` calls `summarize_bundle`, `verify_schedule`, `load_manifest` and `variant_metrics` only, opens no file for writing, never opens the ledger (charged CHF comes from the bundles) and has no network or model client; the bundle writer classes are not used. This is checked, not assumed: the sha256 listing of the 88 files used in 1.5 and 6.2 is taken before and after the extraction and must be identical, and a test runs the analysis on a copied fixture bundle and asserts that the source tree's file list and checksums are unchanged. The extract stores an absolute bundle path like the v2 file; the builder ignores it. The builder reads no bundle, no ledger, no key and no network, so it runs in CI. `started_at` is null in the committed JSON, so the date shown per run (v1 2026-11-03, v2 2026-11-19) is parsed from the run ID prefix and the builder fails on an ID without a date.

**Decision 11: content and headline.** Landscape page, top to bottom: header (headline, sub-line, logo small at the top right), main row, bottom row, limits strip.
- Headline and sub-line are a fixed template whose numbers are read from the data, never typed: "Small samples mislead: at 30 trials per prompt the revised prompt looked better (27/30 -> 29/30); at 100 trials per run both prompts reached 99/100." and "Repeating the same baseline prompt moved the result by 2 trials (99 -> 97); changing the prompt moved it by 0." The builder asserts the facts the sentences state (v1 revised minus baseline > 0; the two v2 runs have equal counts; the repeat differs from the first baseline run by more than that difference) and fails with the reason otherwise, so the text can never state something the data no longer shows.
- Chart (inline SVG): the five runs (v1 baseline, v1 revised, v2 baseline, v2 revised, v2 baseline repeat), one row each, point at the success rate with the Wilson 95% interval as a horizontal bar, `k/n` printed beside each row. One shared axis from 0.70 to 1.00, with the axis start printed on the chart (a truncated axis is stated, not hidden); intervals are taken from the committed JSON (not recomputed; a test cross-checks them with `wilson_interval`). A divider and the run dates separate v1 from v2; the legend states "Wilson 95% interval, trials treated as independent".
- Per-task grid: the ten tasks (rows, benchmark order) by the five runs (columns) as `k/n`; a cell below n/n is filled with the deck's warning colour and bold (not colour alone), and the `lists_02` row is outlined and labelled so that 0/3 in v1 against 9/10 and 10/10 and 9/10 in v2 is visible at a glance (data: v1 baseline 0/3, v1 revised 3/3, v2 9/10, 10/10, 9/10). The task sets and order of both extracts must be identical, else the build fails.
- Failure types per run: failed trials split into formatting failures (`syntax_error` plus `contract_error`) and other failures, as `f/n` per run and kind, headed "small signal, few trials". Facts from the data: v2 baseline runs 4 of 200 formatting failures against 0 of 100 in the revised run; the revised run has 1 other failure (`wrong_answer`). Any failure label other than the two formatting ones counts as other and the builder fails if the labels do not add up to the failed trials.
- Limits strip, fixed wording from the committed claims: the same ten benchmark-informed tasks; one model; trials treated as independent; no significance claim; v1 (2026-11-03) and v2 (2026-11-19) were run on different days, so a change of the provider over time cannot be separated.
- Reported facts only. No sentence says the revised prompt is better or worse; the interpretation is the user's slot.

**Decision 12: the one user-text slot.** `backup_slide/user_text.toml` holds `takeaway = ""` with a header comment that the user writes it and that no tool fills it. Limit 180 characters (about two lines at the slot's font size; the builder counts characters after trimming and fails above the limit). Empty or whitespace-only: the default build prints a clearly visible dashed placeholder box ("Takeaway: to be written by the student") and exits 0; `--require-user-text` (the release flag) exits non-zero while it is empty. The text is HTML-escaped. The builder only reads this file; tests use fixture files and a test asserts that building never opens it for writing. The committed page therefore shows the placeholder until the user writes the text; the page must be rebuilt and committed after that, and `--check` fails if it is not.

**Decision 13: build, determinism, tests.** Plain HTML with inline CSS and inline SVG, no JavaScript and no external request of any kind (fonts: `system-ui`). Byte-deterministic: no timestamps, fixed number formats (`k/n`, rates to 4 decimals as in the JSON), sorted iteration, `\n` line ends. CLI: `build_backup_slide.py build` (writes `backup_slide/backup_slide.html`), `check` (exit 1 with a diff summary when the committed file differs or is missing), both accepting `--require-user-text`, plus path options so tests can point at fixtures. Offline tests (`tests/test_build_backup_slide.py`, fixtures built in `tmp_path` or small committed JSON fixtures, no bundles): headline numbers and the failing assertion when the facts do not hold; five rows and `k/n` labels in the chart; grid has 50 cells and marks `lists_02`; formatting vs other split and the sum check; placeholder, limit and `--require-user-text`; determinism (two builds identical); the committed page equals a fresh build from the committed evidence; the page contains no `<script`, no `http` reference and no external `src`/`href`; the CSS tokens equal `deck.css`; every font size in the page is at least 20px at 1920 (the deck's floor; chart text at least 18px) computed from the cqw sizes; print rule present (`@page` A4 landscape, background colours kept); the logo hash equals the manifest hash; that the presentation is untouched is checked once at the end by `git diff --name-only d3f8fe7..HEAD` (task 7.9), not by a test that would pin the deck forever.

**Decision 14: layout and checks that need a browser.** Geometry follows the deck: a 16:9 box that is the query container, sizes in `cqw` (1cqw = 19.2px at 1920), body text at least 28px where it is sentences, table and chart text at least 20px (chart axis text 18px), nothing scrolls at 1920x1080, a thin right-aligned logo (about 8cqw wide) in the top right corner. Print: `@page { size: A4 landscape; margin: 6mm }`, the slide scaled to the page width, `print-color-adjust: exact`, `break-inside: avoid`. What cannot be tested offline (real rendering, no scroll, legibility from a distance, one printed A4 page) is a coordinator task in section 8 of tasks.md, in the Orca browser at 1920x1080 and by printing.


## Risks / Trade-offs

- [Run-to-run variation makes the revision's difference unreadable] -> That is the finding the repeat exists to measure; the write-up reports baseline-vs-repeat next to baseline-vs-revised and claims nothing beyond the intervals.
- [Code change invalidates earlier evidence] -> Only v2 uses the new evaluator hash; v1 evidence files are not rewritten. v1's probe record becomes stale for re-running v1, which is not planned; v1 bundles and `compare` of v1 runs are unaffected (they compare stored identities).
- [Provider drift or an outage during ~1.5 hours of sequential runs] -> A-B-A bracketing; incomplete runs are preserved, labelled, and stop the sequence (Decision 8).
- [A missed `--config`/`--evidence`/`--bundles` flag spends money on v1's schedule or reads v1 evidence] -> Documented variables; overwrite guards make writes refuse; a v1-config run into the v2 bundle directory could still spend, so the command sequence passes all three flags on every command and `check` is run first; run every command from the worktree root.
- [A forgotten `--no-tracking` records into MLflow] -> `run --experiment` is available and the sequence uses `--no-tracking`.
- [Re-recording probes or the freeze after a code change is refused by the guards] -> Intended: remove the coordinator's own `$EV` file on purpose, never v1's.
- [Code changes between runs] -> `evaluator_code_sha256` mismatch makes the pair not comparable; the sequence forbids edits between runs.
- [Evidence committed with absolute machine paths] -> Accepted by the user for v2; `--smoke-bundle` is always passed explicitly.
