# Design

## Context

Findings from reading the code (not assumptions):

- `experiment.py` fixes `EXPERIMENT_ID = "prompt_comparison_v1"` and `TRIALS_PER_TASK = 3`; `build_config` takes neither as a parameter, and `config_drift` rebuilds with the module constants. The variant set is fixed to `("baseline", "revised")`, in that order, by `parse_config`. `schedule`, `trials_per_task` and `parse_config`'s schedule-length check are already generic, as are `run_recorded` (`trials_per_task` from the configuration) and `verify_schedule`.
- The same variant can be run twice under one experiment: `check_preconditions` rejects a second run of a variant (`prior_run`, read from `<bundle_root>/<run_id>.experiment.json` markers of the same experiment id) unless `--allow-rerun` is given, which is recorded in the marker. Run IDs are chosen by `new_run_id()` (UTC timestamp plus six hex characters); the CLI has no `--run-id`, and the run prints `bundle: <path>`. A bundle is `<bundle root>/<run_id>/`.
- The bundle root is already configurable: `--bundles` on `check`, `run` and `compare`, before the subcommand on `trace_inspect`, and after `record`/`status` on `mlflow_tracking`. Default `run_bundles` is unchanged. No code change is needed for separate bundle storage.
- `check` gates (all recomputed on each start): `cost_acceptance`, `api_key`, `variant_prompt`, `config_current` (configuration against the repository), `container_host`, `benchmark_freeze`, `probes` (probe record bound to the evaluator code hash, which hashes every `*.py` under `src/codegen_eval/`, so any code change in this change invalidates earlier probe records), `settings_frozen` (freeze record must name this experiment id and settings hash), `smoke_trace` and `calibration` (recomputed from the retained smoke bundle named in the freeze record), `budget_projection`, `prior_run`.
- Evidence is read from `--evidence` (default `experiments/evidence/`), where `record-probes` and `freeze-settings` write `probes.json`, `probes.junit.xml` and `settings_freeze.json` with fixed names. Called without `--evidence`, those commands would overwrite the first experiment's record (the freeze record is not checked for its experiment id on write).
- `compare` and `compare_runs` take the variant names from their position (`--baseline`, `--revised`) and verify each bundle against that variant's prompt, so they cannot compare a baseline with a baseline repeat. `_identity_differences` already encodes "only the prompt may differ" and requires equal `schedule_sha256`, `settings_hash` and `evaluator_code_sha256`.
- `record_bundle` (MLflow) takes `experiment=` (default `codegen-eval-runs`, used by v1); `experiment_cli run` offers only `--tracking-uri`/`--no-tracking`, so v2 runs use `--no-tracking` and `mlflow_tracking record --experiment <name>` afterwards, as v1 did.
- The budget projection in `check` is the ledger total plus the worst case of every variant still to run: attempts = trials x (4 model calls + 2 retries per trial) at the pre-send reservation per attempt. It prints nothing unless it fails.

See proposal.md for motivation.

## Goals / Non-Goals

**Goals:**
- Run the A-B-A experiment through the existing preconditions, with the same frozen settings and bundle/evidence formats.
- Make it impossible for the v2 tooling to overwrite v1 configuration, evidence or bundles by a missed flag, and prove the defaults unchanged by tests.
- A deterministic offline analysis with Wilson intervals and a run-to-run comparison.

**Non-Goals:**
- No new paid smoke, no new freeze of different settings, no change to prompts, benchmark, limits, model configuration or the grading code path.
- No change to the presentation, report or their evidence scripts; no change to v1 documents beyond an optional dated pointer note (see Decision 7).
- No significance tests, no claim of improvement, no interleaving implementation (Decision 6).

## Decisions

**1. A separate experiment id, configuration and trial count.** `build_config` and `config_drift` gain `experiment_id` and `trials_per_task` parameters whose defaults are the v1 constants; `build-config` gets `--experiment-id` and `--trials-per-task` (defaults v1) and drift checks rebuild with the recorded values. The configuration `experiments/prompt_comparison_v2.json` is generated by `build-config --experiment-id prompt_comparison_v2 --trials-per-task 10 --revised-prompt baseline_agent_v2 --config experiments/prompt_comparison_v2.json`. Its `settings`, `benchmark` and `variants` sections must equal v1's (a test and a recorded command compare them); only `experiment_id`, `trials_per_task` and `schedule` (100 entries, `task_major`, trial ids `strings_01-t1` ... `-t10`) differ. Alternative considered: reuse the v1 experiment id with 10 trials: rejected, the `prior_run` guard and run markers would collide with v1's, and the v1 configuration would have to change.

**2. Three runs under one experiment: baseline, revised, baseline `--allow-rerun`.** The existing `prior_run` precondition already treats a repeat as a recorded decision; the third run's marker records `allow_rerun: true`. The v2 bundle directory holds exactly three runs (`<id>` + `<id>.experiment.json` each), so the first two have no prior run of their variant. Alternative: a third variant name `baseline_repeat`: rejected, it widens `parse_config`, `verify_schedule` and `compare_runs` for a variant that is the baseline, and the identical variant name is what makes the three bundles pass the same schedule, prompt and identity checks.

**3. Storage: v2 writes only to its own paths.**
- Bundles: `$P/run_bundles_v2/` where `$P` is the primary checkout (`/Users/jolbax/Developer/devspace/cas_aml_mlops_project`), next to but never inside `run_bundles/`, so they survive the removal of any worktree, like the retained v1 bundles. Passed as `--bundles`.
- Evidence: `$P/experiments/evidence_v2/` (probes, junit, settings freeze), passed as `--evidence` on every command that reads or writes it (`record-probes`, `freeze-settings`, `check`, `run`).
- `.gitignore` gains `/run_bundles_v2/` and `/experiments/evidence_v2/` in this change. Until the branch is merged, the primary checkout's own ignore file does not have them (open question 2).
- MLflow: same service, experiment name `codegen-eval-prompt-comparison-v2` (`mlflow_tracking record --experiment ...`), so the v1 runs in experiment `codegen-eval-runs` are not touched. A separate store would need a second container (`MLFLOW_DATA_DIR`, port, name) for no added protection, because recording never edits other runs.
- Retained smoke evidence is reused read-only: `freeze-settings --smoke-bundle $P/run_bundles/20261103T050806Z-30949f` (the v1 smoke bundle; `calibrate` only reads it and checks model-config hash and image). The settings and model are identical, so a new paid smoke is not needed; the freeze record for v2 names this bundle and its manifest digest.

**4. Overwrite guards (the only changes to existing commands).** `write_config` refuses to overwrite an existing file whose `experiment_id` differs from the new data's; `write_settings_freeze` refuses when an existing freeze record in the target directory names another experiment. Both messages name the path and both ids. `write_probes_evidence` is bound to code, not to an experiment, so it is protected by always passing `--evidence` (documented command sequence, Decision 8) rather than by a guard. Alternative: derive the evidence directory from the experiment id automatically: rejected as larger, since `record-probes` does not load a configuration today. Tests prove: defaults unchanged (v1 `build-config --check` passes, `build_config()` with no arguments equals the recorded v1 sections, default `--bundles` is `run_bundles`), and the guards leave the target byte-identical.

**5. Analysis: `codegen_eval.scale_analysis`, offline, no model client, no ledger, no sandbox.** `python -m codegen_eval.scale_analysis --config C --bundles B --baseline RUN_A --revised RUN_B --repeat RUN_C [--json]`. For each run it calls the existing `summarize_bundle`, `verify_schedule(bundle, config, variant)` (A and C as baseline, B as revised) and `variant_metrics`, so the figures are the same as `compare`'s; adds per-task `k/10` and the Wilson 95% interval for `primary.count / primary.of`:

    centre = (p + z^2/(2n)) / (1 + z^2/n);  half = z * sqrt(p(1-p)/n + z^2/(4n^2)) / (1 + z^2/n);  z = 1.959964

reported to four decimals, `[max(0, centre - half), min(1, centre + half)]`. It then reports two pairs with identical rules to `compare_runs` (identity check through `_identity_differences`, both runs headline-eligible, otherwise "not comparable" with reasons): baseline vs revised (the effect of the prompt plus any drift) and baseline vs repeat (variation of the same prompt, plus drift over the same span). Each pair lists the difference in successes, gained/regressed/unchanged tasks and whether the two Wilson intervals overlap, nothing else: no p-values and no "significant". Output is plain text or sorted-key JSON, identical on every call for the same bundles (no timestamps of its own). `compare_runs`, `variant_metrics` and `render_comparison` are not changed; the module imports the first two of those and the private `_identity_differences` within the same package. `experiment_cli compare` stays usable for baseline vs revised of v2 (`--config` and `--bundles` pointing at v2). Wilson with n = 100 trials ignores that the ten trials of one task are correlated and the tasks are not a random sample; the write-up says so. Tested with fixture bundles built like those in `tests/test_experiment.py` plus unit tests of the interval (0/100, 100/100, 50/100, 29/30 against the formula).

**6. Interleaving at trial level: not built.** `run_variant` writes one bundle per variant with the variant and prompt in the bundle identity, and `verify_schedule`, `compare_runs` and MLflow recording all assume one prompt per bundle. Alternating the prompts inside one schedule would need a different runner, two bundles written concurrently (or a mixed-prompt bundle format) and changes to every verifier: not small. Trade-offs if built later: it would cancel provider drift exactly per task (the best control), but sequential A-B-A with a repeat already brackets drift and measures run-to-run variation, which interleaving alone does not. A-B-A stays the default.

**7. v1 documents.** v1 files are not edited. If the user wants a pointer from `docs/prompt_comparison.md` to the v2 comparison, only one dated note line is added at the end of the document in the follow-up that writes the v2 results; this change adds none now and says so in its report.

**8. Command sequence for the coordinator** (all from the worktree root of the branch carrying the implementation, at its final commit; `src/codegen_eval/*.py` must not change between the first `record-probes` and the last run, because the evaluator code hash is compared across the three runs and with the probe record). Shell variables:

    P=/Users/jolbax/Developer/devspace/cas_aml_mlops_project
    CFG=experiments/prompt_comparison_v2.json
    B=$P/run_bundles_v2
    EV=$P/experiments/evidence_v2
    SMOKE=$P/run_bundles/20261103T050806Z-30949f
    PR=~/.codegen_eval/pricing_2026-11-03.json
    X="PYTHONPATH=src .venv/bin/python -m codegen_eval.experiment_cli"

Once (free, offline except Podman, no key): `build-config --check --config $CFG` must say "configuration matches the repository"; `record-probes --config $CFG --evidence $EV` (Podman probe suite; counts must have skipped=0); `freeze-settings --config $CFG --evidence $EV --smoke-bundle $SMOKE --note "v2: settings and smoke of v1 reused"`.

Per run N (1 baseline, 2 revised, 3 baseline with `--allow-rerun`), in this order, waiting for each to finish:
1. `$X check --variant V --config $CFG --evidence $EV --bundles $B --pricing $PR --smoke-bundle $SMOKE --i-accept-cost` must print `all preconditions hold` (the key is read from the environment by the CLI, as in v1).
2. `$X run --variant V [--allow-rerun for run 3] --config $CFG --evidence $EV --bundles $B --pricing $PR --smoke-bundle $SMOKE --i-accept-cost --no-tracking`; note the printed `bundle:` and run ID.
3. `PYTHONPATH=src .venv/bin/python -m codegen_eval.trace_inspect --bundles $B verify RUN_N` must say COMPLETE, 100 of 100.
4. Stop and ask the user if `complete=False`, the exit status is not 0, or the printed `CHF 10 checkpoint reached` is `True`.

After the three runs: `mlflow_tracking record RUN_N --bundles $B --tracking-uri http://127.0.0.1:5001 --experiment codegen-eval-prompt-comparison-v2` for each (service up, free), then `$X compare --config $CFG --bundles $B --baseline RUN_1 --revised RUN_2` and `PYTHONPATH=src .venv/bin/python -m codegen_eval.scale_analysis --config $CFG --bundles $B --baseline RUN_1 --revised RUN_2 --repeat RUN_3` (text and `--json`).

**9. Projected cost** (offline, `PriceInputs.reservation_chf` with `~/.codegen_eval/pricing_2026-11-03.json` and the model configuration `openrouter_glm_v1`: 12,000 input and 2,000 output tokens per attempt, margin 0.25): CHF 0.0008197 per attempt. A run is at most 100 x (4 + 2) = 600 physical attempts. What `check` compares with the CHF 15 ceiling is the ledger total (read by the CLI, not by this change; about CHF 0.0068 after v1 according to the v1 write-up) plus, for run 1, the worst case of both variants not yet done (1,200 attempts, CHF 0.9836), for run 2 the revised variant (600 attempts, CHF 0.4918), for run 3 the repeat (600 attempts, CHF 0.4918). Worst case for all three runs: 1,800 attempts, CHF 1.4755 (v1's equivalent was 360 attempts, CHF 0.2951 plus the ledger total, the CHF 0.2962 recorded). Expected spend is far lower: v1 charged CHF 0.00275 and 0.00297 for 30 trials, so about CHF 0.009 to 0.010 per 100-trial run, about CHF 0.03 for all three. The worst case exceeds the user's stop threshold of CHF 1 while the expected spend is about thirty times below it (open question 1).

## Risks / Trade-offs

- [Run-to-run variation makes the revision's difference unreadable] -> That is the finding the repeat exists to measure; the write-up reports baseline-vs-repeat next to baseline-vs-revised and claims nothing beyond the intervals.
- [Code change invalidates earlier evidence] -> Only v2 uses the new evaluator hash; v1 evidence files are not rewritten. v1's probe record becomes stale for re-running v1, which is not planned; v1 bundles and `compare` of v1 runs are unaffected (they compare stored identities).
- [Provider drift or an outage during ~1.5 hours of sequential runs] -> A-B-A bracketing; incomplete runs are preserved, labelled, and stop the sequence (Decision 8).
- [A missed `--config`/`--evidence`/`--bundles` flag spends money on v1's schedule or reads v1 evidence] -> Documented variables; overwrite guards make writes refuse; a v1-config run into the v2 bundle directory could still spend, so the command sequence passes all three flags on every command and `check` is run first.
- [Code changes between runs] -> `evaluator_code_sha256` mismatch makes the pair not comparable; the sequence forbids edits between runs.
- [Untracked ignore entries in the primary checkout until merge] -> `git status` there shows the two directories as untracked; harmless, noted for the coordinator.

## Migration Plan

Additive. Rollback is deleting this branch; v1 files, bundles, evidence, ledger and MLflow experiment are never written. After the user decides to merge, the coordinator pushes and merges; the v2 runs can be done on this branch before that.
