### Verified flow, read from the code at commit `37968d8`

This is the control flow the diagrams must show. Each line names the function it was read from; stage 2 re-verifies every line, and the twins cite the functions.

**Start and gates (`experiment_cli.main`, `experiment.check_preconditions`)**
- `experiment_cli.main` parses `run --variant {baseline,revised} --pricing ... --i-accept-cost` (argparse exits 2 on bad arguments); `load_config` reads `experiments/prompt_comparison_v1.json`, and an `ExperimentError`, `BundleError`, `ValueError`, or `OSError` there prints `error: ...` and returns **1**. Before the run, an unreadable pricing file, an unusable model config, or a missing MLflow client (`ImportError` building `bundle_recorder`) return `REFUSED` (**2**) with `refusing to run: ...`. With `--no-tracking` no recorder is built.
- `experiment.run_variant` calls `check_preconditions` first, before any client, marker, or bundle exists, and raises `PreconditionsFailed` listing all failures together. The checks, in code order: cost acceptance, API key present, variant exists and has a versioned prompt (the revised prompt is `null` in the configuration today, so a `revised` run is refused), configuration drift against the repository (`config_drift`), host platform equals the recorded container platform and its pinned image, benchmark freeze (`tasks.check_freeze` plus a recorded freeze hash), probe evidence (`probes_problems`: junit counts, evaluator code hash, image, retained report hash), settings freeze with retained smoke bundle and re-computed calibration (`calibrate`), budget projection (ledger total plus the worst-case attempts of every variant still to run, times the per-attempt reservation, must stay within the CHF 15 ceiling), and no earlier run of this variant unless `--allow-rerun` (an unreadable marker blocks too). `experiment_cli.main` maps `PreconditionsFailed` to `REFUSED` (2) and prints each failure.
- The same function backs the offline `check` subcommand, which stops after printing the unmet checks.

**Run setup (`run_variant`)**
- Loads the variant's prompt, the model config, and the frozen benchmark; builds the grader with `replay.make_grader()` (that is `evaluate.grade_trial` bound to `sandbox.run_case`) unless one is injected; creates the run id; reads the ledger state.
- Writes the experiment run marker `<bundle_root>/<run_id>.experiment.json` with status `started` **before** any trial runs, so a crash always leaves a marker.
- Calls `run_recording.run_recorded(...)` with `client_for`, built in `experiment_cli.main` as an `OpenRouterClient` per trial with the ledger, prices, key, and the context (experiment, variant, task, trial).

**Schedule loop (`run_recorded`)**
- `run_recorded` builds its own `planned` list, `tasks x trials_per_task` in task order (`experiment.build_schedule` builds the same list for the configuration, and `verify_schedule` compares the two; 10 tasks x 3 trials = 30 trials per variant, `trial_order` `task_major`). `BundleWriter` writes `manifest.json` with status `in_progress` first.
- For each planned trial: build the client (`client_for`), wrap it in `RecordingClient` with a sink to `BundleWriter.append_call` (each request is appended to `<trial>.calls.jsonl`, fsynced, **before** it is sent, each response as soon as it returns), call `trial.run_trial`, grade with `grader(task, result)` (which is `evaluate.grade_trial`), then `BundleWriter.write_trial` (atomic trial record, hash into the manifest, the partial call log is deleted).
- After each trial: if `result.infrastructure_status == budget_ceiling`, record the stop reason and `break`. Every other infrastructure outcome (for example `transport_exhausted`, `api_error`) does **not** stop the loop; the next trial runs.
- After the loop (or on break) `BundleWriter.finish` verifies the bundle record by record (`verify_bundle`) and stores manifest status `complete` or `incomplete` with the reasons. On any `BaseException` in the loop (Ctrl-C, ledger or bundle error, an unexpected exception) `finish(["interrupted: <type>"])` runs and the exception is re-raised.

**One trial (`trial.run_trial`)**
- Fresh conversation: system prompt plus task instruction and signature (no hidden cases). `while model_calls < max_model_calls (4)`: increment the call counter; tools are enabled (`tool_choice: auto`) only while `model_calls < 4` and `tool_attempts < max_tool_attempts (3)`; the last call, and any call after the allowance is spent, is `tool_choice: none`, and `OpenRouterClient._payload` then still sends the tool definitions so the history's tool calls stay valid; `client.complete(request)`.
- Response handling, five outcomes in code order: `ModelFailure` with kind `request_rejected` ends the trial `no_submission`/`request_rejected` (call consumed, nothing sent); any other `ModelFailure` (including `budget_ceiling`, `transport_exhausted`, `api_error`, `malformed_response`) ends it `infrastructure_incomplete` with that status; a tool request while tools are disabled ends it `no_submission`/`tool_request_when_disabled`; a tool request while enabled runs `_handle_tool_calls` and the loop continues; no content ends it `no_submission`/`no_final_message`; otherwise the content is the final submission, checked by `contract.validate_source` and the trial ends `submitted` (a contract issue is recorded, never repaired).
- `_handle_tool_calls`: one response is one attempt (`tool_attempts += 1`); only the first call **named** `run_checks` executes (not merely the first call), every other call gets error feedback in the same turn; `run_checks.run_checks` validates the arguments (`parse_request`: payload bytes, JSON shape, at most `max_checks_per_request (4)` checks), validates the source contract, then calls `sandbox.execute_check` once per check (one fresh container each) and compares actual with the agent's expected value in trusted code. An infrastructure status from a check ends the trial `infrastructure_incomplete` with no feedback message sent for that call (`_handle_tool_calls`: `continue`).

**One model call (`openrouter_client.OpenRouterClient.complete`)**
- Build the payload, compute `input_token_bound`; above `max_input_tokens` it records `pre_send_rejected` and returns `ModelFailure(request_rejected)` **without** reserving or sending. Otherwise, for each physical attempt: `ledger.reserve` (durable, fsynced, under an exclusive lock; the ceiling test is `state.total + amount > ceiling`, total being committed plus outstanding reservations) **before** `transport.post` to the OpenRouter endpoint; `BudgetCeiling` records a `refusal` and returns `ModelFailure(budget_ceiling)`. After the reply: `ledger.settle` with the reported cost or a labelled estimate, or `ledger.keep` when the charge is uncertain (timeout, missing usage, error). A transient failure (timeout, connection error, HTTP 408/429/5xx) retries up to `max_retries_per_request` and `max_retries_per_trial`, each retry reserving again; otherwise `ModelFailure(transport_exhausted)`.
- Ledger checkpoint (CHF 10) is logged once by `_log_checkpoint`, called from `reserve`, `settle`, and `adjust`, when reserved plus committed reaches it; nothing stops, so the checkpoint belongs to the ledger, not to the send. The ceiling (CHF 15) refuses the reservation that would exceed it.

**Grading (`evaluate.grade_trial`, `sandbox.run_case`/`execute_check`, `worker.py`)**
- `grade_trial` grades the final submission only. `infrastructure_incomplete` and `no_submission` trials and contract failures run no container (all four checks unexecuted). Otherwise each of the four cases runs through `run_case` = `execute_check` (a `payload_too_large` outcome returns before any container starts and is an unexecuted candidate outcome, not an infrastructure one, so containers start per **executed** case): `podman create` with the hardened flags, `podman start --attach`, the payload (source, function name, one case's arguments, a per-check token, limits) on stdin, the supervisor in the container (`worker.SUPERVISOR`) runs the executor, which reports on a private pipe with the token; the host reads one bounded JSON result, removes the container, and `evaluate.score_case` compares it with the expected answer on the host. Infrastructure outcomes make the trial `incomplete`.

**After the loop (`run_variant`, `experiment_cli.main`)**
- `verify_schedule` checks the bundle against the configured schedule; `record_run(bundle, variant)` (`mlflow_tracking.bundle_recorder`) runs **once per run, after the bundle is finalized**: `record_bundle` verifies the bundle and uploads it; on `TrackingUnavailable`, `ImportError`, or `BundleError` it writes the outage marker `tracking.json` (status `not_recorded`) and returns a message, and `run_variant` catches any other `Exception` as `tracking failed (...)`. MLflow results are never read back; `record_bundle` does search MLflow (`_find_run`) for an earlier upload of the same bundle digest so recording is idempotent, then uploads. A tracking outcome never changes the run status. `record_bundle` runs `verify_bundle` without finalizing and blocks only on `_BLOCKING` problems, so an incomplete bundle (`run_not_finalized`, `missing_record`) **is** uploaded; `tracking.json` says `recorded`, or `not_recorded` only on an outage, a missing client, or a blocking problem.
- The marker is rewritten with status `complete` or `incomplete`, then `main` prints the bundle, ledger totals, checkpoint flags, tracking text, and schedule problems, and returns 0 if `result.complete` (bundle verification clean and schedule ok) else 1.
- Not part of `run` (the lifecycle around it is described next): `compare` (`comparison.compare_runs`, which calls `summary.summarize_bundle` and `verify_schedule` on two finished bundles and reads bundles only), human review of the result summaries, and `scripts/build_work_log.py`.



**Lifecycle around `run` (commands that exist today; `README.md` "Prompt-comparison experiment tooling")**
1. Setup, each its own command: `scripts/freeze_benchmark.py --check` (benchmark freeze, `tasks.check_freeze`); `experiment_cli build-config [--check]` (`experiment.build_config`, `config_drift`); `experiment_cli record-probes` (`run_probe_suite`, Podman probes, evidence under `experiments/evidence/`); `openrouter_cli smoke --pricing ... --i-accept-cost` (one PAID smoke trial, the retained smoke bundle, PHASE 2); `experiment_cli calibrate --smoke-bundle B` (`experiment.calibrate`); `experiment_cli freeze-settings --smoke-bundle B` (`write_settings_freeze`, refuses unless calibration passes); optionally `scripts/mlflow_service.sh start` (an outage never blocks a run); `experiment_cli check --variant V` (`check_preconditions` only: prints each unmet check, exit 1 if any, nothing spent).
2. `experiment_cli run --variant baseline ...` (the sub-activity).
3. Human inspection of the baseline failures, read-only and without a model call: `trace_inspect list|verify|show RUN`, optionally `replay RUN` (Podman re-grading) and `mlflow_tracking status`.
4. The human writes the revised prompt file `src/codegen_eval/prompts/<version>.md`, then `experiment_cli build-config --revised-prompt <version>`. `check_preconditions` refuses the revised variant while its `prompt_version` is `null` (`variant_prompt`) or the configuration is stale (`config_current`). Probe evidence and the settings freeze stay valid because `evaluator_code_sha256` and `settings_hash` exclude prompt files. Then `experiment_cli check --variant revised`.
5. `experiment_cli run --variant revised ...` (the same sub-activity).
6. `experiment_cli compare --baseline RUN_A --revised RUN_B` (`comparison.compare_runs` calls `summary.summarize_bundle` and `verify_schedule` on two finished bundles; bundles only; exit 0 only if `headline_comparison`, otherwise the figures are printed labelled not a headline comparison and the exit is 1).
7. Human review of the comparison and the reviewed result summary (PENDING in the logical diagram), then `scripts/build_work_log.py` (and `--check`).

## Goals / Non-Goals

**Goals:**
- A reader can see when the whole experiment starts and finishes, the gates, the single `run` command expanded as a sub-activity, the order inside one trial, and every ending, and a reviewer can check each node against a function.
- The two accepted diagrams stay byte-identical; the new views line up with their box names, trust boundary, and phase marking.
- Drift is caught offline by tests; the sanitizer is not weakened.

**Non-Goals:**
- No runtime code, CI, or accepted-diagram change; no diagram generation from code in the repository (the authoring script is not committed); no results, spend, run identifiers, or live-run claims; no new dependency (draw.io is an authoring tool only).

## Decisions

### 1. Two new files; authoring rules include explicit fills and edge label backgrounds

`docs/run_flow_activity.drawio.svg` (main) and `docs/run_flow_sequence.drawio.svg` (supplement), each with a twin (`docs/run_flow_activity.md`, `docs/run_flow_sequence.md`), exported with the documented flags (`-x -f svg --embed-diagram --svg-theme light --embed-svg-fonts false`) under the authoring rules of the accepted change (`html=0`, no `whiteSpace`, no images, gradients, shadows, links, Helvetica only) **plus two rules found by the review spike**: every vertex sets an explicit `fillColor` (never the default white, which exports `light-dark(#ffffff, var(--ge-dark-color, #121212))` and fails the unchanged sanitizer), and every edge sets `labelBackgroundColor=none`. Alternatives for the content: extend the logical diagram (rejected: accepted, must not change) or a two-page `.drawio` (an SVG export renders only the first page).

### 2. The activity diagram is the experiment lifecycle, with `run` as an expanded sub-activity

The diagram has one start node (the experiment begins) and one final node (the experiment is complete), and the top-level flow follows the lifecycle above: setup commands, the offline `check`, the `run --variant baseline` call-behaviour action (drawn as a bold-bordered action marked `[sub-activity: see frame below]`, without the rake glyph), human inspection, revised prompt and `build-config`, `check`, the `run --variant revised` call-behaviour action, `compare`, human review, work-log rebuild. Each node carries its real command and function. Both `run` actions point to the same expanded activity, drawn once in a dashed frame "activity: run --variant V (one invocation)" in the same diagram (an SVG export renders one page only), which holds the content of the earlier proposal: the pre-run refusals, `check_preconditions` with its gates (cost acceptance and key, variant prompt, `config_drift` and platform and image, benchmark freeze, probe evidence, settings freeze with smoke bundle and calibration, budget projection against CHF 15, no earlier run), the run marker, the schedule loop, the agent loop, the grading loop, the bundle, the post-loop `finish`, `verify_schedule`, the MLflow recording with the outage marker, and the marker finalisation. The differences from the original briefing stay drawn as the code behaves: one `run` runs one variant (two invocations), MLflow is recorded once per run after the bundle is finalized (not per trial), and `compare` (with `summarize_bundle`), human review, and the work-log rebuild are separate commands outside `run`. The sub-activity's **completed** outcome is not a final node: it is the exit edge back to the lifecycle.

### 3. Endings: seven final nodes, each with its observable record

The run sub-activity has four final nodes (UML final node, `shape=endState`); completed is the exit edge:
1. **Refused** (drawn in the host CLI lane): `experiment_cli.main` returns `REFUSED` (2) for an unreadable pricing file, an unusable model config, or a missing MLflow client, and `PreconditionsFailed` from `run_variant` returns `REFUSED` (2); an unreadable or invalid configuration returns 1 with `error: ...` (and argparse exits 2). In every case nothing is written: no marker, no bundle, no client, no ledger event (the ledger file may be created empty when opened).
2. **Budget ceiling**: a trial's `ModelFailure(budget_ceiling)`: that trial is graded and recorded as `infrastructure_incomplete`, the loop breaks, later trials are not run; manifest `incomplete` with reason `budget_ceiling`; marker `incomplete`; exit 1. MLflow recording is still attempted and succeeds for the incomplete bundle (`run_not_finalized` and `missing_record` are not blocking); `tracking.json` says `recorded`, or `not_recorded` only on an outage.
3. **Incomplete after infrastructure outcomes** (any other `infrastructure_incomplete` trial such as `transport_exhausted` or `api_error`, a hidden check that hit `infrastructure_error` or `protocol_error`, or schedule problems): the loop continued, `verify_bundle` reports `infrastructure_stop`; manifest `incomplete`; marker `incomplete`; exit 1; MLflow recording attempted as above. Ending 2 versus 3 is a decision after the loop on the recorded stop reason.
4. **Aborted**: any `BaseException`, with three observable variants the twin lists. (a) Inside `run_recorded` after the writer exists (Ctrl-C, `LedgerError`, `BundleError`, `FixtureExhausted`, unexpected exception): `finish(["interrupted: <type>"])` stores manifest `incomplete`, the marker is rewritten `interrupted`. (b) Before the writer exists but after the marker (`load_prompt`, `load_benchmark`, `build_identity`, `BundleWriter` raising `bundle already exists`): the marker is `interrupted` and there is no bundle, or an `in_progress` one. (c) After `run_recorded` returned (`verify_schedule` raising `BundleError`, `ledger.state()` raising `LedgerError`, the final `atomic_write`): the bundle manifest is already finalised and the marker stays `started`. In all variants the exception leaves `main` with a traceback (only `PreconditionsFailed` is caught around `run_variant`).

The lifecycle adds three final nodes: **`check` unmet** (`experiment_cli check` prints each unmet precondition, exit 1, nothing spent), **`compare` not headline** (`headline_comparison` false: figures printed with reasons, exit 1), and **experiment complete**.

Not endings, drawn as actions that continue: the **CHF 10 checkpoint** (logged once by the ledger from `reserve`/`settle`/`adjust`, reported in the final printout as `checkpoint_reached`) and an **MLflow outage** (`tracking.json` `not_recorded`; run status unchanged). Wrong-answer, `no_submission`, and `infrastructure_incomplete` trials other than the ceiling are normal recorded trials, not endings. The completion decision is `verification.complete and schedule.ok`. If stage 2 finds a further ending in the code it adds a final node and records it.

### 4. Swimlanes, boundary marking, and the mapping to the logical diagram

Lanes are named by the logical-diagram boxes they hold, so the views line up:

| Lane | Logical-diagram boxes | Status shown in the header |
|---|---|---|
| human (manual steps) | reviewed result summaries (and the human's own steps) | PENDING |
| host CLI (trusted process) | `experiment.py + experiment_cli.py`, `run_recording.py` (the trial and recording code), `trial.py`, `run_checks.py`, `evaluate.py + contract.py`, `sandbox.py + limits.py`, `comparison.py`, `summary.py`, `scripts/build_work_log.py` | PARTIAL: NO LIVE RUN YET (the weakest status of its boxes) |
| OpenRouter (EXTERNAL) | `openrouter_client.py` talks to it; `OpenRouter (external model API)` | EXTERNAL, PHASE 2, PENDING |
| sandbox container (TRUST BOUNDARY) | `worker.py` | IMPLEMENTED |
| on disk and MLflow | `run_recording.py + bundle.py` (run bundles, run marker), `ledger.py` (file), `mlflow_tracking.py`, `MLflow tracking store` | PARTIAL: NO LIVE RUN YET |

Status is carried by the lane (and sequence lifeline) headers, one of the three labels of the logical diagram or the external tag; action and message nodes carry no status. Decision nodes carry the limit values as text (four model calls, three tool attempts, four checks per request) from `agent_config.AgentLimits`. The ledger and the run marker are host-side files, shown in the disk lane with the reserving and settling actions in the host lane. The candidate container lane is the only trust-boundary region; no flow leaves it except to the host launcher.

The sequence diagram carries the agent-loop detail; the activity diagram keeps the loop regions at the level of reserve, send, settle, outcome, tool check, final submission, grading, record. Nothing is placed that the code does not do; where the code is ambiguous, stage 2 asks the coordinator.

### 5. Sequence diagram: participants, fragments, order

Participants (lifelines, named by module with the logical box in the header and the status): `experiment.py / run_recording.py` (`run_variant`, `run_recorded`), `trial.py`, `openrouter_client.py` (as the `model_client.py` `ModelClient`), `ledger.py`, `OpenRouter` (EXTERNAL, PHASE 2), `run_checks.py`, `sandbox.py` (host launcher), `worker.py` (container, inside the trust-boundary frame), `evaluate.py`, `bundle.py`, `mlflow_tracking.py`.

Order for one trial: `run_recorded` creates the client and `RecordingClient`, calls `run_trial`; `loop` while `model_calls < 4`: `complete(request)` (tools enabled only while calls and tool attempts are left, else `tool_choice: none` with the tool definitions still sent) → request appended to the call log (`bundle.append_call`, fsynced, before the send) → `input_token_bound` check → `alt` too large (`request_rejected`: no reserve, no send) / otherwise per attempt `ledger.reserve` → POST to OpenRouter → reply → `ledger.settle` or `ledger.keep` → `alt` transient failure with a retry left (reserve again) / final; the response is appended to the call log → `alt` with the five outcomes of `run_trial` in code order: (1) `ModelFailure(request_rejected)` → `no_submission`; (2) other `ModelFailure` → `infrastructure_incomplete`; (3) tool call while tools are disabled → `no_submission` (`tool_request_when_disabled`); (4) tool call while enabled → `run_checks.run_checks` → `loop` per check `execute_check` → container → bounded result → host compares → feedback to `trial.py`, or an infrastructure status ends the trial with no feedback; (5) no content → `no_submission` (`no_final_message`), else final content → `validate_source` → `submitted`. Then `grade_trial` → `alt` no container for `no_submission`, `infrastructure_incomplete`, or a contract issue / otherwise `loop` per executed case (up to four) `run_case` → `execute_check` (`podman create`, `start --attach`, stdin payload with the token, the worker's single report, the host removes the container) → `score_case` on the host → `write_trial` (atomic record, manifest hash). A note after the trial, outside its frame, shows `mlflow_tracking.record_bundle` once per run after `finish` and `verify_schedule` (idempotent: it searches for an earlier upload of the same digest, then uploads; results are never read back). The trust boundary is a dashed frame around `worker.py` with the two crossing arrows labelled with the data; there is no message between the frame and any lifeline except `sandbox.py`.

UML conventions: `shape=umlLifeline` lifelines, `shape=umlFrame` fragments with operator labels (`loop`, `alt`) and guard text, no activation bars. The review spike showed these export inside the sanitizer allowlist.

### 6. Tests (`tests/test_run_flow_diagrams.py`, new; accepted tests untouched)

Helpers are copied into the new test module so `tests/test_architecture_diagrams.py` stays unmodified; de-duplicating is a recorded follow-up. `tests/test_work_log_diagrams.py` needs one update: its repository test asserts the exact list of registered diagram ids and the figure count, so those two assertions now name the four diagrams and five figures; nothing else in it changes. Checks, offline, no Podman, no draw.io:
- Both files parse, the embedded XML decodes uncompressed, labels equal rendered text (multiset of lines), both files pass `sanitize_drawio_svg` unchanged, and `light-dark(#ffffff, var` does not occur in them.
- Every `*.py`, `*.sh` and `module.function`/`function()` name written in a label or twin exists (AST lookup in `src/codegen_eval/`; `scripts/`).
- Structure: exactly one cell with `shape=startState`; final nodes are the cells with `shape=endState` and there are exactly seven, with the titles of decision 3; every final node has an incoming edge and no outgoing one; every swimlane and lifeline header contains one of the three status words or the `EXTERNAL` tag; the OpenRouter lane and lifeline carry `EXTERNAL` and `PHASE 2`; no arrow connects a box in the container lane to a box in another lane except the one to and from the host launcher; lane names are the logical-diagram box names listed in decision 4.
- Constants and limits: `REFUSED`, `STATUS_COMPLETE`, `STATUS_INCOMPLETE`, the marker strings `started`, `interrupted`, `complete`, `incomplete`, the `tracking.json` strings `recorded` and `not_recorded`, `budget_ceiling`, `tool_request_when_disabled`, `no_final_message`, `request_rejected` exist in the source; limits in labels equal `DEFAULT_AGENT_LIMITS`, `CHECKPOINT_CHF`, and `CEILING_CHF`; the twin states the exit status for each ending.
- Order claims against the source (AST or text positions): in `OpenRouterClient._attempt`, `ledger.reserve` precedes `transport.post`; in `RecordingClient.complete`, the request is emitted before `inner.complete`; in `run_variant`, the marker `atomic_write` precedes `run_recorded`, which precedes `verify_schedule`, which precedes `record_run`; in `run_recorded`, `grader` precedes `write_trial`; `comparison.py` and `summary.py` do not import `mlflow`; `run_variant` is the only caller of `check_preconditions` besides `experiment_cli check`.
- Twins: every vertex title and edge label appears in its twin; no invented result, run identifier, spend, or URL (same regex and allowlist as the accepted test).
- Work log: a small test builds the work log with the new entries and asserts they follow the existing diagrams with `role="img"`, title, description, twin, and provenance rows; the repository `build_work_log.py --check` covers the real files. That the accepted diagrams and twins are unchanged is checked by `git diff --stat` in the acceptance task.

### 7. Work-log registration and sanitizer

Two new `[[diagram]]` tables (`run-flow-activity`, `run-flow-sequence`, `label = "current"`) after the existing two. `sanitize_drawio_svg`, `validate_svg`, `SVG_TAGS`, and the allowlist stay unchanged: the review spike exported every UML shape used here (swimlane, `startState`, `endState`, rhombus, dashed loop region, `umlLifeline`, `umlFrame`, labelled solid and dashed edges) with only `svg g rect ellipse path text defs`, passing once decision 1's two rules are applied. If the real export still fails, the order of attempts stays: change the authoring, then a reviewed, tested allowlist addition recorded here, then the link-plus-twin fallback for that diagram. The activity diagram is large (about 70 nodes); its SVG is checked for size well under the 16 MB page limit.

## Risks / Trade-offs

- [The briefing's wording differs from the code on variants, MLflow granularity, and summary/comparison] → Decision 2 draws the code and states the differences in the twin; the worker report tells the coordinator so the user can confirm.
- [The lifecycle activity diagram is very dense] → Lanes, an expanded frame, and the sequence supplement carry the detail; stage 2 renders PNGs and looks at them for legibility; if still too dense, loop detail moves to the sequence diagram and lifecycle steps and endings stay.
- [The real export fails the sanitizer] → Decision 1's two authoring rules and the test that runs `sanitize_drawio_svg`; the decision 7 order of attempts.
- [A further ending exists that this reading missed] → Task 2.1 re-derives the endings from the code; the test pins the constants; a Fable review checks the list.
- [Diagrams drift when the code changes] → The source-checking tests and a "verified against commit" line in each twin.
- [Two test modules share copied helpers] → Accepted; follow-up once the accepted change's tests may be edited.
- [Status misread as a result] → Same markers as the physical diagram, a `no live run has happened` line, the regex test for invented evidence.

## Migration Plan

Additive: new files and two optional `[[diagram]]` entries. Roll back by removing the entries and files. The change is not archived by stage 2; archiving follows user acceptance.

None that change the specs or tasks; layout choices (band order, node placement) are settled while drawing and judged in the acceptance task.
