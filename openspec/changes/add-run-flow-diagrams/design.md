### Verified flow, read from the code at commit `37968d8`

This is the control flow the diagrams must show. Each line names the function it was read from; stage 2 re-verifies every line, and the twins cite the functions.

**Start and gates (`experiment_cli.main`, `experiment.check_preconditions`)**
- `experiment_cli.main` parses `run --variant {baseline,revised} --pricing ... --i-accept-cost`; `load_config` reads `experiments/prompt_comparison_v1.json`. Before the run: unreadable pricing file, unusable model config, or a missing MLflow client (`ImportError` building `bundle_recorder`) return `REFUSED` (2) with `refusing to run: ...`. With `--no-tracking` no recorder is built.
- `experiment.run_variant` calls `check_preconditions` first, before any client, marker, or bundle exists, and raises `PreconditionsFailed` listing all failures together. The checks, in code order: cost acceptance, API key present, variant exists and has a versioned prompt (the revised prompt is `null` in the configuration today, so a `revised` run is refused), configuration drift against the repository (`config_drift`), host platform equals the recorded container platform and its pinned image, benchmark freeze (`tasks.check_freeze` plus a recorded freeze hash), probe evidence (`probes_problems`: junit counts, evaluator code hash, image, retained report hash), settings freeze with retained smoke bundle and re-computed calibration (`calibrate`), budget projection (ledger total plus the worst-case attempts of every variant still to run, times the per-attempt reservation, must stay within the CHF 15 ceiling), and no earlier run of this variant unless `--allow-rerun` (an unreadable marker blocks too). `experiment_cli.main` maps `PreconditionsFailed` to `REFUSED` (2) and prints each failure.
- The same function backs the offline `check` subcommand, which stops after printing the unmet checks.

**Run setup (`run_variant`)**
- Loads the variant's prompt, the model config, and the frozen benchmark; builds the grader with `replay.make_grader()` (that is `evaluate.grade_trial` bound to `sandbox.run_case`) unless one is injected; creates the run id; reads the ledger state.
- Writes the experiment run marker `<bundle_root>/<run_id>.experiment.json` with status `started` **before** any trial runs, so a crash always leaves a marker.
- Calls `run_recording.run_recorded(...)` with `client_for`, built in `experiment_cli.main` as an `OpenRouterClient` per trial with the ledger, prices, key, and the context (experiment, variant, task, trial).

**Schedule loop (`run_recorded`)**
- `planned` is `tasks x trials_per_task` in `task_major` order (`experiment.build_schedule`; 10 tasks x 3 trials = 30 trials per variant). `BundleWriter` writes `manifest.json` with status `in_progress` first.
- For each planned trial: build the client (`client_for`), wrap it in `RecordingClient` with a sink to `BundleWriter.append_call` (each request is appended to `<trial>.calls.jsonl`, fsynced, **before** it is sent, each response as soon as it returns), call `trial.run_trial`, grade with `grader(task, result)` (which is `evaluate.grade_trial`), then `BundleWriter.write_trial` (atomic trial record, hash into the manifest, the partial call log is deleted).
- After each trial: if `result.infrastructure_status == budget_ceiling`, record the stop reason and `break`. Every other infrastructure outcome (for example `transport_exhausted`, `api_error`) does **not** stop the loop; the next trial runs.
- After the loop (or on break) `BundleWriter.finish` verifies the bundle record by record (`verify_bundle`) and stores manifest status `complete` or `incomplete` with the reasons. On any `BaseException` in the loop (Ctrl-C, ledger or bundle error, an unexpected exception) `finish(["interrupted: <type>"])` runs and the exception is re-raised.

**One trial (`trial.run_trial`)**
- Fresh conversation: system prompt plus task instruction and signature (no hidden cases). `while model_calls < max_model_calls (4)`: increment the call counter; tools are enabled only while `model_calls < 4` and `tool_attempts < max_tool_attempts (3)` (the last call and any call after the allowance is spent is `tool_choice: none`); `client.complete(request)`.
- Response handling, in code order: `ModelFailure` with kind `request_rejected` ends the trial `no_submission`/`request_rejected` (call consumed, nothing sent); any other `ModelFailure` (including `budget_ceiling`, `transport_exhausted`, `api_error`, `malformed_response`) ends it `infrastructure_incomplete` with that status; a tool request while tools are disabled ends it `no_submission`/`tool_request_when_disabled`; a tool request while enabled runs `_handle_tool_calls` and the loop continues; no content ends it `no_submission`/`no_final_message`; otherwise the content is the final submission, checked by `contract.validate_source` and the trial ends `submitted` (a contract issue is recorded, never repaired).
- `_handle_tool_calls`: one response is one attempt (`tool_attempts += 1`); only the first `run_checks` call executes, other calls get error feedback in the same turn; `run_checks.run_checks` validates the arguments (`parse_request`: payload bytes, JSON shape, at most `max_checks_per_request (4)` checks), validates the source contract, then calls `sandbox.execute_check` once per check (one fresh container each) and compares actual with the agent's expected value in trusted code. An infrastructure status from a check ends the trial `infrastructure_incomplete` with no feedback sent.

**One model call (`openrouter_client.OpenRouterClient.complete`)**
- Build the payload, compute `input_token_bound`; above `max_input_tokens` it records `pre_send_rejected` and returns `ModelFailure(request_rejected)` **without** reserving or sending. Otherwise, for each physical attempt: `ledger.reserve` (durable, fsynced, under an exclusive lock) **before** `transport.post` to the OpenRouter endpoint; `BudgetCeiling` records a `refusal` and returns `ModelFailure(budget_ceiling)`. After the reply: `ledger.settle` with the reported cost or a labelled estimate, or `ledger.keep` when the charge is uncertain (timeout, missing usage, error). A transient failure (timeout, connection error, HTTP 408/429/5xx) retries up to `max_retries_per_request` and `max_retries_per_trial`, each retry reserving again; otherwise `ModelFailure(transport_exhausted)`.
- Ledger checkpoint (CHF 10) is logged once by `_log_checkpoint` when reserved plus committed reaches it; nothing stops. The ceiling (CHF 15) refuses the reservation that would exceed it.

**Grading (`evaluate.grade_trial`, `sandbox.run_case`/`execute_check`, `worker.py`)**
- `grade_trial` grades the final submission only. `infrastructure_incomplete` and `no_submission` trials and contract failures run no container (all four checks unexecuted). Otherwise each of the four cases runs through `run_case` = `execute_check`: `podman create` with the hardened flags, `podman start --attach`, the payload (source, function name, one case's arguments, a per-check token, limits) on stdin, the supervisor in the container (`worker.SUPERVISOR`) runs the executor, which reports on a private pipe with the token; the host reads one bounded JSON result, removes the container, and `evaluate.score_case` compares it with the expected answer on the host. Infrastructure outcomes make the trial `incomplete`.

**After the loop (`run_variant`, `experiment_cli.main`)**
- `verify_schedule` checks the bundle against the configured schedule; `record_run(bundle, variant)` (`mlflow_tracking.bundle_recorder`) runs **once per run, after the bundle is finalized**: `record_bundle` verifies the bundle and uploads it; on `TrackingUnavailable`, `ImportError`, or `BundleError` it writes the outage marker `tracking.json` (status `not_recorded`) and returns a message, and `run_variant` catches any other `Exception` as `tracking failed (...)`. MLflow is never read back and a tracking outcome never changes the run status.
- The marker is rewritten with status `complete` or `incomplete`, then `main` prints the bundle, ledger totals, checkpoint flags, tracking text, and schedule problems, and returns 0 if `result.complete` (bundle verification clean and schedule ok) else 1.
- Not part of `run`: `compare` (`comparison.compare_runs`, which calls `summary.summarize_bundle` and `verify_schedule` on two finished bundles and reads bundles only), human review of the result summaries, and `scripts/build_work_log.py`. They are manual follow-up steps in the activity diagram, drawn as such.

## Goals / Non-Goals

**Goals:**
- A reader can see the start, the gates, the loop, the order inside one trial, and every ending, and a reviewer can check each node against a function.
- Two accepted diagrams stay byte-identical; the new views line up with their box names, trust boundary, and phase marking.
- Drift is caught offline by tests; the sanitizer is not weakened.

**Non-Goals:**
- No runtime code, CI, or accepted-diagram change; no generation of diagrams from code; no results, spend, run identifiers, or live-run claims; no new dependency (draw.io is an authoring tool only).

## Decisions

### 1. Two new files, one activity diagram as the main view and one sequence diagram as the supplement

`docs/run_flow_activity.drawio.svg` and `docs/run_flow_sequence.drawio.svg`, each with a twin (`docs/run_flow_activity.md`, `docs/run_flow_sequence.md`), exported with the documented flags (`-x -f svg --embed-diagram --svg-theme light --embed-svg-fonts false`) under the authoring rules (`html=0`, no `whiteSpace`, no images, gradients, shadows, links, Helvetica only). Alternatives: extend the logical diagram (rejected: it is accepted and must not change) or one two-page `.drawio` (an SVG export renders only the first page).

### 2. The activity diagram follows what `run` does, and states where the user's mental model differs from the code

Three points differ from the briefing wording and are drawn as the code behaves; each is stated in the twin:
1. **Variants are not one loop inside one command.** One `run --variant X` runs one variant's schedule into one bundle. The experiment is two separate `run` invocations (`baseline`, then `revised`) and then `compare`. The diagram shows the per-run flow once, framed "repeat once per variant, as separate commands: `--variant baseline`, then `--variant revised`", and draws the comparison after both bundles exist. The schedule order (`task_major`, 3 trials per task) is stated on the loop node. Today the `revised` run is refused by `variant_prompt` because its prompt is unset; the twin says so as a status line, not as a flow element.
2. **MLflow is recorded once per run, not per trial**, after the bundle is finalized and `verify_schedule` ran. The per-trial order is: trial record written to the bundle, next trial. The run-level order is: bundle finalized, schedule verified, MLflow recording attempt (with the outage marker), marker status written.
3. **Summary and comparison are not called by `run`.** They belong to the `compare` command (`compare_runs` calls `summarize_bundle`); human review and the work-log rebuild are manual. They sit in a lane "after the run (separate commands)" so the diagram does not suggest `run` performs them.

### 3. Endings: five final nodes plus two non-endings, each stated with its observable record

Final nodes (UML final node, an ellipse inside an ellipse), each labelled with its status words:
1. **Completed** (`result.complete`): CLI exit 0; manifest `complete`; marker `complete`; tracking text states recorded or not recorded.
2. **Refused by preconditions** (`PreconditionsFailed` in `run_variant`, or the three refusals before it in `main`): exit `REFUSED` (2); no marker, no bundle, no client, no ledger entry from this run. The three pre-run refusals are one node with the failing check list in the twin.
3. **Budget ceiling** (a trial's `ModelFailure(budget_ceiling)`): the trial is graded and recorded as `infrastructure_incomplete`, the loop breaks, later trials are not run; manifest `incomplete` with reason `budget_ceiling`; marker `incomplete`; exit 1; MLflow recording still attempted for the partial bundle.
4. **Incomplete after infrastructure outcomes** (trials ended `infrastructure_incomplete` for other reasons such as `transport_exhausted` or `api_error`, or a hidden check hit `infrastructure_error`/`protocol_error`): the loop continued, `verify_bundle` reports `infrastructure_stop`; manifest `incomplete`; marker `incomplete`; exit 1.
5. **Aborted** (any `BaseException` in `run_recorded`, for example Ctrl-C, a `LedgerError`, a `BundleError`, an unexpected exception): `finish(["interrupted: <type>"])` stores manifest `incomplete`, the marker is rewritten `interrupted`, the exception propagates out of `main` (there is no handler around `run_variant` except `PreconditionsFailed`), so the process ends with a traceback.

Not endings, drawn as actions that continue: the **CHF 10 checkpoint** (logged once by the ledger, reported in the final printout as `checkpoint_reached`), and an **MLflow outage** (marker `tracking.json`, text in the marker; run status unchanged). Wrong-answer or `no_submission` trials are normal graded trials, not endings. Ending 4 versus 1 is decided by `verification.complete and schedule.ok`; the diagram shows that as one decision after the loop. The implementation task re-reads these statuses from the code and a test pins them (decision 6) so a changed status wording fails offline. If stage 2 finds a sixth ending in the code, it adds a final node and records it; none was found in this reading.

### 4. Swimlanes and boundary marking

Lanes, left to right, named like the logical diagram's boxes so the views line up: **host CLI** (`experiment_cli.py`, `experiment.py`, `run_recording.py`, `trial.py`, `run_checks.py`, `evaluate.py`, `sandbox.py`, `comparison.py`/`summary.py`, `build_work_log.py`), **OpenRouter (EXTERNAL, PHASE 2)** (dashed outline, with the key and the ledger reservation shown as host-side actions before the send), **sandbox container (TRUST BOUNDARY)** (`worker.py`; only candidate source plus one case's arguments in, only a bounded result out; no arrow to any other lane except the host launcher), **storage and MLflow** (`bundle.py`, `ledger.py` file, experiment marker, `mlflow_tracking.py`, MLflow service, `tracking.json`). The ledger belongs to the host (a file read and written by the host process), shown in the storage lane, with reserve and settle actions drawn in the host lane crossing to it. Status labels (`IMPLEMENTED`, `PARTIAL: NO LIVE RUN YET`, `PENDING`) are not repeated per action; instead each lane header carries the status of its module(s) from `docs/progress.md`, and the OpenRouter lane carries `PENDING, PHASE 2: no live call has been made`. Decision nodes carry the limit values as text (four model calls, three tool attempts, four checks per request) taken from `agent_config.AgentLimits` and checked by a test.

To keep the diagram readable at roughly 30 to 45 nodes, the agent loop and the grading each use one loop region (UML interruptible-region style as a dashed rounded rectangle labelled `loop`) and the detail of message order lives in the sequence diagram. Nothing is placed that the code does not do; where the code is ambiguous, stage 2 asks the coordinator rather than choosing.

### 5. Sequence diagram: participants, fragments, order

Participants (lifelines, named by module, with the logical-diagram box name in the header): `experiment.py / run_recording.py` (`run_variant`, `run_recorded`), `trial.py`, `openrouter_client.py` (as `ModelClient`), `ledger.py`, `OpenRouter` (EXTERNAL, PHASE 2), `run_checks.py`, `sandbox.py` (host launcher), `worker.py` (container, inside the trust-boundary frame), `evaluate.py`, `bundle.py`, `mlflow_tracking.py`. `model_client.py` is the interface name on the `trial.py` to `openrouter_client.py` messages.

Message order for one trial (each message a function call from the code reading above): `run_recorded` creates the client and `RecordingClient`, calls `run_trial`; `loop` while the call budget is left: `complete(request)` → append request to the call log (`bundle.append_call`) → `input_token_bound` check → `alt` rejected (no reserve, no send) / sent: per attempt `ledger.reserve` → POST to OpenRouter → response → `ledger.settle` or `ledger.keep` → `alt` transient failure with retry left (loop reserve again) / final; the response is appended to the call log → `alt` on the outcome: `ModelFailure` ends the trial; tool request: `run_checks` → `loop` per check `execute_check` → container → bounded result → host compares → feedback to `trial.py`, back to the loop; final content: `validate_source`, trial ends. Then `grade_trial` → `alt` no container for `no_submission` / `infrastructure_incomplete` / contract issue, else `loop` per case (four) `run_case` → `execute_check` → container (`podman create`, `start --attach`, stdin payload with the token, worker report, host removes the container) → `score_case` → `write_trial` (atomic record, manifest hash). A note after the trial (outside the trial frame) shows that `mlflow_tracking.record_bundle` is called once per run after `finish`, with a reference to the activity diagram. The trust boundary is a dashed frame around `worker.py` with the two arrows crossing it labelled with the data; there is no message between the frame and any other lifeline except `sandbox.py`.

UML conventions: lifelines are `shape=umlLifeline`, activations are omitted (they add no information here and add export shapes), fragments are `shape=umlFrame` with operator labels `loop`, `alt`, and guard text. These shapes are chosen for the draw.io export; the spike (task 1.1) confirms they stay inside the sanitizer allowlist or switches to plain rectangles, lines, and rounded dashed rectangles drawn with the same labels.

### 6. Tests (`tests/test_run_flow_diagrams.py`, new; accepted tests untouched)

Helpers are the same functions as in `tests/test_architecture_diagrams.py`, copied into the new test module (or a new `tests/diagram_support.py` imported only by it) so the accepted test file stays unmodified; de-duplicating is a recorded follow-up. Checks, offline, no Podman, no draw.io: both files parse and the embedded XML decodes uncompressed; labels equal rendered text (the same multiset-of-lines rule); every `*.py` and function name written in a label or twin exists (`name.py`, and `module.function` or backticked `function()` names resolve by AST in `src/codegen_eval/`); each of the five endings is a final node (ellipse-in-ellipse pair by cell style) and its label and twin line state the exit status and statuses that the code produces, with the constants (`REFUSED`, `STATUS_COMPLETE`, `STATUS_INCOMPLETE`, marker strings `started`, `interrupted`, `complete`, `incomplete`, `not_recorded`, `budget_ceiling`) asserted present in the source; the limits in the labels equal `DEFAULT_AGENT_LIMITS`, `CHECKPOINT_CHF`, and `CEILING_CHF`; order claims asserted against the source as AST or text-position facts (in `OpenRouterClient._attempt` `ledger.reserve` precedes `transport.post`; in `RecordingClient.complete` the request is emitted before `inner.complete`; in `run_variant` the marker `atomic_write` precedes `run_recorded`, and `run_recorded` precedes `record_run`; in `run_recorded` `write_trial` follows `grader` and `run_trial`; `comparison.py` and `summary.py` do not import `mlflow`); lane and participant names from the logical diagram appear in the new twins; the OpenRouter lifeline and lane carry `EXTERNAL` and `PHASE 2`; the container is the only trust-boundary region and no arrow connects a box inside it to a box outside it other than the host launcher (`sandbox.py`); no invented result, run identifier, spend, or URL (the same regex and allowlist as the accepted test); the accepted diagrams and twins are unchanged is checked by the acceptance task by `git diff --stat` against the base, not by a test. Work-log: `tests/test_work_log_diagrams.py` is not modified; the new registered diagrams are covered by the repository `--check` run and by a small test in the new module that builds the work log with them and asserts they appear after the existing diagrams with `role="img"`, title, description, and twin.

### 7. Work-log registration and sanitizer

Two new `[[diagram]]` tables (`run-flow-activity`, `run-flow-sequence`, `label = "current"`) after the existing two. `sanitize_drawio_svg`, `validate_svg`, `SVG_TAGS`, and the allowlist stay unchanged unless the real export of a UML shape needs a construct outside them. The order of attempts is the one decided before: first change the authoring (plain shapes, `html=0`, no markers) to avoid it; only then, if strictly needed, propose an addition in this design, review it (Fable), and test that every previously rejected input is still rejected. The fallback is link-plus-twin for the offending diagram, as already documented. Large diagrams are checked for size (the accepted pair is tens of kilobytes; the 16 MB page limit is not a concern).

## Risks / Trade-offs

- [The briefing's wording differs from the code on variants, MLflow granularity, and summary/comparison] → Decision 2 draws the code and states the differences in the twin; the coordinator is told in the worker report so the user can confirm before acceptance.
- [The activity diagram becomes too dense to read] → Loop regions plus the sequence supplement carry the detail; stage 2 renders PNGs and the coordinator re-views them as for the accepted pair (task 2.5); if it stays dense the lane contents are reduced, not the endings.
- [UML shapes export with a construct outside the sanitizer allowlist] → Spike first (task 1.1); authoring change, then a reviewed allowlist addition, then the fallback (decision 7).
- [A fifth or sixth ending exists that this reading missed] → Task 2.1 re-derives the endings by walking `experiment_cli.main`, `run_variant`, `run_recorded`, `run_trial`, and the client, and the endings test pins the status constants; a Fable review checks the list.
- [Diagrams drift when the code changes] → The source-checking tests of decision 6 and a "verified against commit" line in each twin.
- [Two test modules share copied helpers] → Accepted; follow-up to share them once the accepted change's tests may be edited.
- [Status misread as a result] → Same markers as the physical diagram, `no live run has happened` line, regex test for invented evidence.

## Migration Plan

Additive: new files and two optional `[[diagram]]` entries. Roll back by removing the entries and files. The change is not archived by stage 2; archiving follows user acceptance.
