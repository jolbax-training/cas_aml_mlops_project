{{user:motivation}}

Problem statement

Scores reported for coding agents are hard to trust. These things go wrong, and the project is built around closing each one:

  • Unsafe candidate code. The agent writes code that has to be run to be judged, and running untrusted code can reach credentials, the host or the scoring itself.
  • Flaky or hidden cost. Paid model calls add up unnoticed, and a retry loop can spend more than was planned.
  • Irreproducible results. A score without the exact code, prompt, settings and saved transcripts cannot be checked again by someone else.
  • Small-sample claims. A few trials per task cannot tell a real difference from run-to-run noise, yet they are often reported as if they could.

The headline of this work is therefore a trustworthy, reproducible, budget-safe evaluation pipeline for a coding agent, not a better agent.

Approach

{{fig:diagram-pipeline-overview}}

Budget-safe paid calls

All paid calls share one ledger. The worst-case cost is reserved before each request; one that would pass the ceiling is never sent. A checkpoint of CHF {{val:protocol.checkpoint_chf|chf}} lets work continue, a ceiling of CHF {{val:protocol.ceiling_chf|chf}} stops it. Ledger total after both runs: CHF {{val:protocol.ledger_total_chf|chf4}} (rounded to four decimals; the exact value is quoted in the comparison document).

{{fig:diagram-trust-boundary}}

Scoring integrity

Each check runs in a fresh Podman container: no network, read-only filesystem, dropped capabilities, unprivileged user, limits on time, memory and processes. It gets only the source, the function name and one check's arguments; expected answers and the comparison stay on the host.

What the isolation probes cover

The probes target the protected assets of the threat model: {{val:protocol.probe_categories.0}}; {{val:protocol.probe_categories.1}}; {{val:protocol.probe_categories.2}}; {{val:protocol.probe_categories.3}}; and {{val:protocol.probe_categories.4}}. One accepted residual: code that walks the executor's frames can forge a report, but expected answers never enter the container, so a forged value is no better than a returned one.

Experiment design

{{val:protocol.tasks}} tasks in {{val:comparison.baseline.categories|count}} categories, {{val:protocol.trials_per_task}} trials per task and variant, {{val:comparison.baseline.hidden_checks.of}} hidden checks per variant. One model, fixed sampling, one prompt sentence changed.

Reproducibility

Every run is saved as a local bundle, with a recorded digest, before any tracking happens. Traces can be inspected with no model API or container. Grading replay reruns saved final candidates in Podman with no model call and no credentials; it regrades, it is not a new agent trial. A completeness check confirms every planned trial was recorded ({{val:provenance.runs.baseline.completeness.recorded}} of {{val:provenance.runs.baseline.completeness.planned}} for the baseline, {{val:provenance.runs.revised.completeness.recorded}} of {{val:provenance.runs.revised.completeness.planned}} for the revised run). Both runs are recorded as traces in a local MLflow service.

Limits, lessons and conclusions

Limits

{{limits}}

Lessons learned

  • Large integers in traces. A few traces could not be read back because check arguments held integers outside the tracking server's range; they are now stored as decimal strings, and all traces were re-recorded.
  • Forced last call in a smoke run. Unforced smokes never reached the final-only call; a smoke-only instruction did. A forced trace says nothing about model quality.
