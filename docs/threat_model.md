# Candidate execution threat model

Scope: one untrusted, model-generated Python function call per check, executed by `src/codegen_eval/sandbox.py`. This is an engineering control for a course project, not a production security certification. Evidence is the probe suite in `tests/test_isolation_probes.py` and `tests/test_execution_limits.py`; observed results are recorded in [progress](progress.md).

## Assets

| Asset | Why it matters |
| --- | --- |
| Hidden expected answers and scoring code | Candidate must not see them or influence the verdict beyond its own return value |
| Credentials, API keys, host environment | Candidate must not read or exfiltrate them |
| Tracking services and repository files | Candidate must not reach MLflow, the network, or host files |
| Podman control | Candidate must not reach the Podman socket or other containers |
| Score integrity | Candidate must not forge a result or hide that it mutated its inputs |

## Attacker capability

Arbitrary Python (standard library only passes `validate_source`, but probes bypass it) running as an unprivileged user inside one container for at most the deadline. The attacker does not know the per-check token, expected answers, or other checks' inputs.

## Protections

- **Fresh container per check**, uniquely named, removed explicitly after the check (no `--rm`, so `State.OOMKilled` can be read first). Cleanup is outside the deadline, and late-created containers are retried.
- **No inputs beyond source, function name, and one check's arguments.** `execute_check` has no expected-value parameter; a unit test inspects the payload. Comparison runs in `evaluate.py`.
- **Container flags:** `--network=none`, `--read-only`, no extra tmpfs, `--cap-drop=ALL`, `no-new-privileges`, user 65534, no mounts/secrets/env files/devices/host namespaces, no Podman socket; only `HOME=/tmp` in the environment. Writable `/tmp` is `noexec` and 16 MiB.
- **Limits** (`ExecutionLimits`, hashable and serialisable): 10 s deadline from process start including container startup and code loading; 128 MiB memory (swap equal); 1 CPU; 32 processes; 64 KiB source-plus-arguments rejected before any container starts; 32 KiB print output (counted for `print`, `sys.stderr`, and raw descriptor writes); 64 KiB worker report.
- **Worker integrity (design decision).** Candidate code and the reporter used to share one Python process and stdout, so a candidate could write a fabricated success message and `os._exit(0)`, or patch `json.dumps` to hide an input mutation. Both were demonstrated against the pilot (see progress) and are fixed by three layered choices, selected from the options in design.md:
  1. A **supervisor** is the container's PID 1 and the only writer of the real stdout. It marks itself non-dumpable (`PR_SET_DUMPABLE=0`), so same-user candidate code cannot read `/proc/1/{mem,environ,fd}` and, being PID 1 with SIGINT reset to `SIG_DFL` (CPython's default handler would otherwise raise `KeyboardInterrupt`; verified by a probe sending ten signals to PID 1), the kernel discards signals sent from inside the container. The per-check **token** arrives on its stdin, never in argv or the environment.
  2. A separate **executor** process runs the candidate and sends exactly one report on a private pipe, signed with the token. The supervisor rejects anything else on that pipe (wrong or missing token, extra bytes, unexpected fields) as `protocol_violation`, a candidate outcome. A process that exits without reporting is `protocol_violation` (clean exit) or `candidate_crash` (signal/non-zero).
  3. The executor serialises the return value and post-call arguments with a self-contained encoder whose builtins and helpers are bound before candidate code loads, accepting only exact JSON types. Patching `json`, `sys.modules`, or `builtins`, or returning list subclasses, does not change what is reported; subclass tricks end as `serialization_error`. The trusted side compares the reported post-call arguments with its own copy of the arguments.
- **Supervisor robustness.** Everything the executor can emit is untrusted input to the supervisor: the report is parsed rejecting non-finite constants and catching `RecursionError`; the encoder caps nesting at depth 100 independent of the recursion limit; the supervisor's own response is re-serialised under the 64 KiB protocol cap (forged `1E9` expansion becomes `output_limit`); and any failure after the executor has started becomes `protocol_violation`. Candidate output and behaviour on the supervisor's channels cannot produce an infrastructure outcome. Probes: signals to PID 1, 30 000-deep return, forged NaN/`1e400`/expanding/deep reports.
- **Attribution.** Only the supervisor can write to the container's stdout, so malformed or missing supervisor output, container start failure, or unavailable Podman are infrastructure outcomes (`infrastructure_error`, `protocol_error`). Exceptions, timeouts, print/report overflow (including overflow followed by an exception), mutation, forged reports, and crashes are candidate outcomes. Because the candidate shares the executor process with the reporter, a missing/malformed executor report is charged to the candidate; a genuine executor defect would look like a candidate failure, so a trivial correct candidate must be `returned` (explicit probe).

## Residual limitations

- **In-process introspection.** The token and report pipe live in the executor's own memory. Candidate code that deliberately walks the executor's frames or garbage-collected objects (`sys._getframe`, `gc`) can recover the token and descriptor and sign a false report, including one that hides mutation (demonstrated in review with `sys._getframe(1).f_locals["emit"]`). No in-process design prevents this; the separate supervisor only stops forgery that does not first compromise the executor. **Accepted, not an unresolved bypass:** mutation is judged on net post-call state, so a candidate that deep-copies its input and restores it is honestly "no mutation" and a forged report can claim nothing more. Expected answers never enter the container, so a forged value is no better than a returned one, exceptions and silence are reachable honestly, and the forged-report subset that could force infrastructure outcomes (NaN, overflow, expansion, nesting) is closed and probed. The delta spec's concealed-mutation scenario states these net-state semantics.
- **Not defended:** Podman, libkrun/VM, or kernel escapes; side channels and timing; CPU contention inflating timeouts; resource exhaustion that makes the host VM unstable beyond the cgroup limits.
- **Deadline sensitivity.** Startup (about 0.7 s per check on the recorded macOS VM) consumes part of the 10 s deadline; a loaded host could turn a slow-but-correct candidate into a timeout. Re-measure per environment.
- **Environment coverage.** Probes were run only where recorded in progress (macOS arm64, Podman VM). A Linux or CI runner needs its own run before its results are trusted. The pinned image digest is the only image checked.
- **Runner confinement differs from the laptop (CI, Ubuntu 24.04, Podman 4.9.3, rootful, crun, AppArmor).** On the first two GitHub runs the 14 failing probes had one pattern: every signal sent from inside a container (a candidate's `os.kill`, its own `SIGKILL`, and the supervisor's `child.kill()` on output overflow, which surfaced as `infrastructure_error`) failed with `EPERM`. The deductions are: the failures include a process signalling itself, which no uid or user-namespace difference can deny, and the laptop's Fedora CoreOS VM uses SELinux, not AppArmor. The cause is the Ubuntu AppArmor default container profile, **confirmed** by run 41128433037's kernel audit line: `apparmor="DENIED" operation="signal" … profile="containers-default-0.57.4-apparmor1" … signal=usr1 peer="containers-default-0.57.4-apparmor1//&crun"`, i.e. the profile's own signal rule did not match the container's label under crun. `scripts/ci_ensure_container_signals.sh` probes this with the sandbox's own flags; only if signalling fails does it set Podman's default `apparmor_profile` to `unconfined` for that job and re-probe, failing with diagnostics if it still fails. All other confinement (dropped capabilities, `no-new-privileges`, default seccomp, read-only root, no network, namespaces, cgroup limits, non-dumpable supervisor) is identical, and no assertion was relaxed: signals to PID 1 must still leave the check undisturbed. Consequently CI evidence for these probes is for "AppArmor-unconfined plus the above", not for AppArmor-confined containers; the CI run's `Container signals` annotation states which case applied.
- **Container removal on Podman 4.x.** `podman rm -f` waits ten seconds for the stop signal before killing, but PID 1 ignores that signal, so the sandbox's own five-second cleanup timeout aborted removal and left containers (five were left on the runner). Removal now passes `--time=0` (immediate kill, 10 s call timeout) on all versions.
- **Cleanup race.** If Podman creates a container after the client was killed at the deadline, removal is retried for a few seconds; a leaked container after that is possible but was not observed.
- **Memory exhaustion and the supervisor.** The cgroup OOM killer picks the largest process, so a candidate spreading memory over many small processes (28 × 4.5 MB in the probe) can get PID 1 killed (exit 137). Mitigations: the executor sets `oom_score_adj=1000` (defence in depth only, since an unprivileged process can lower it again), and the host reads `podman inspect` `State.OOMKilled` before removing the container and records a non-zero exit with an OOM kill as `candidate_crash` ("container memory limit exceeded"). Probes cover both the plain and the score-reset variants. An OOM-killed candidate is otherwise indistinguishable from other signal deaths.
- **Lone surrogates in returned values.** A candidate can return `"\ud800"`; it is scored correctly (`wrong_answer`), but any later writer that persists `CaseResult.actual` must use `ensure_ascii=True` or `errors="backslashreplace"`, because strict UTF-8 encoding would raise on candidate-controlled data. Hand-off note for the results-persistence changes.
